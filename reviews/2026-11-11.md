## 2. 核心知识讲解

### ① 混合检索的融合策略：向量为主 + BM25 补位（为什么不用 RRF）

**是什么**：RAG 检索不只用一种路。向量路做语义召回，BM25 路做词面精确召回，两条路结果要融合成一个排名。今天定下的策略是：向量结果排前面，BM25 结果按 union 追加在后面（不插队、不抢位）；向量路挂了就降级纯 BM25。

**为什么**：这是 69 chunk 实测跑出来的，不是拍脑袋：
- 向量路（doubao-embedding-vision）改述/实体/裸实体查询全 5/5 命中，连裸 commit 哈希这种「不像人话」的查询也第 1 命中；
- BM25 是纯词面匹配，改述后词面变了就召回不了（2/5 落空）；
- 等权 RRF（Reciprocal Rank Fusion）反而不行——弱路（BM25）召回的噪声条目名次被抬起来，把强路（向量）的准确名次拖累，整体检索质量下降。

**怎么用**：融合是「强路保序 + 弱路补位」，不是「两路等权混排」。工程上配合幂等索引（id=docId:chunkIndex）、对账（条数不符自动整库重灌）、熔断（连败 3 次降级）、开关（PA_KB_VECTOR=0 回基线）一起用，保证任何时刻都有可用检索。

**和什么相关**：RAG 检索策略、ChromaDB、嵌入模型、上一轮（11-05）的 BM25 知识库检索。教训是**先验要拿实验推翻**（PITFALLS #63：07 期先验认为向量不靠谱，那是带着「只测 BM25」的隐含条件得出的，融合方式本身才是被测对象）。

### ② Vue 3 的 Ref 裸用陷阱 + 类型检查盲区

**是什么**：Vue 3 的 `ref()` 在**模板里自动解包**（`{{ pendingConfirm }}` 直接用），但在 **script 里不会**——`pendingConfirm` 拿到的是 Ref 对象，`.value` 才是值。今天 ChatPane 里 `pendingConfirm` 在 script 裸用：`messages.length` 是 undefined，`undefined - 1 = NaN`，循环 `i < NaN` 恒 false、循环零次 → 确认弹窗永远不弹。更糟的是此前所有 plan/composite/remember 的确认卡其实全在走「两分钟超时自动拒绝」兜底，没人发现。

**为什么 tsc 没拦住**：`tsc` 默认不检查 `.vue` 文件（Vue SFC 是自定义格式，需要 `vue-tsc` 才检查），裸用 Ref 在类型上不报错（Ref 对象也能访问属性），所以静默漏网。这是 70a3d6f 同款坑第二次咬人。

**怎么用/怎么防**：script 里一律 `.value`；同类问题配套修的两个时序/事件坑：
- 输入框卡高：`submit` 里同步调 resize() 量高，但 v-model 清空是下一帧才落 DOM，量到的还是旧 scrollHeight → `await nextTick()` 再量；
- 「最新」按钮不挂：内容不满一屏且 scrollTop=0 时，窗口最大化/输入框收回让视口变大不触发 scroll 事件 → 补 recheck（可滚动余量 ≤0 无条件贴底）+ ResizeObserver（滚动区尺寸变化）+ 消息 watch（nextTick 后）双触发。

**和什么相关**：Vue 3 响应式原理、模板编译（自动解包是模板编译器的糖）、前端类型检查链路（tsc vs vue-tsc）、DOM 布局时序（v-model 与渲染帧）。

## 4. 参考答案

**Q1**：策略是向量结果保序在前、BM25 结果 union 追加在后不抢位，向量路故障降级纯 BM25。依据是 69 chunk 真机实测：向量路改述/实体/裸实体查询全 5/5 命中（裸 commit 哈希也第 1）；BM25 是词面匹配，改述后词面变了只命中 2/5；等权 RRF 会把弱路召回噪声的名次抬起来，拖累强路的准确名次，整体变差。所以融合不是等权混排，是「强路保序 + 弱路补位」。

**Q2**：幂等靠 id=docId:chunkIndex（同一个 chunk 重复写入落同一位置，天然去重）；自愈靠对账——search 返回条数与索引计数对不上时判定索引不完整，自动整库重灌（带并发闸，同轮多个查询只触发一次重建）；连续失败 3 次进程内熔断，复活后重试；任何异常自吞降级纯 BM25，保证检索永远可用。另有 PA_KB_VECTOR=0 环境开关回基线。嵌入模型换名建集合，天然隔离。

**Q3**：指 07 期「向量检索不靠谱」的先验，其实是在只测 BM25、没把向量纳入被测范围的隐含条件下得出的结论；今天把「融合方式」本身当作被测对象重新实验，发现向量路全 5/5 无盲区、RRF 反被弱路拖累，先验被推翻。教训：结论要标注它成立的前提条件，换条件（比如加一条检索路）就得重新验证，不能拿旧结论当默认值。

**Q4**：现象是写入确认弹窗从未弹出，plan/composite/remember 的确认卡其实全在走两分钟超时自动拒绝兜底。根因是 ChatPane 的 pendingConfirm 在 script 里裸用 Ref：messages.length 为 undefined，undefined-1=NaN，循环条件 i<NaN 恒 false、循环零次，弹窗永不出现。tsc 默认不检查 .vue 文件（需要 vue-tsc），且 Ref 对象本身有属性访问不报类型错，所以静默漏网——70a3d6f 同款坑第二次咬人。修复：补 `.value`。配套纪律：script 里用 Ref 一律 .value；.vue 的类型问题要过 vue-tsc 或靠实测冒烟。

**Q5**：服务端在流式响应里量「流开始到第一个 delta 帧」之间的时延（即用户体感等多久开始出字），随 done 帧下发并落进账本（StoredMessage/NewMessage/sessionDetail 全链路带 ttftMs，刷新换会话仍在），前端署名行展示「首字 0.4s · 总 3.2s」。在服务端量是为了排除前端渲染噪音，量的是纯服务端出字时延。plan/composite 不流 delta 就没有「第一个 delta 帧」这个概念，字段自然为 undefined，JSON 序列化丢弃、前端不显示——不硬造数字。
