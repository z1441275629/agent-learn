## 2. 核心知识讲解

### ① 「预置话题库」vs「自动发现 RSS」的取舍

为什么不用搜索引擎自动发现？因为 B 路线没有搜索引擎，而且**RSS 源的可信度必须实测**：状态 200 不等于源活着，反爬页（36kr/zhihu）返回 200 但 0 items；超时（NYT/BBC）也算死源。实测方法用 Node fetch 同链路（和应用同一套解压逻辑），curl 不带 --compressed 收的是 gzip 字节、grep 不到 item 是假阴性。

产品上「预置 curated 话题 + 自定义话题自动配检索源」= 把「找源」这个高门槛动作从用户手里拿走：预置话题源已配好（运营者帮你找），自定义只填话题名（检索源 hn/github/arxiv 自动配，query=话题名）。前端从「填源表单」变成「chips 多选」，预设 focus 收进折叠详情可微调。

### ② 密码重置的安全设计（与邀请码同构）

- **码与用户名绑定**：拿别人的码改不了别人的号。
- **先验后消费**：弱密码拒绝时码不消费（不能让别人用弱密码试探烧掉你的码）；单次使用，重放拒。
- **串行队列原子窗**：并发请求下码的「验证+消费」要原子，防竞态双花。
- **重置成功吊销全部旧 session**：密码都丢了，旧会话不可信——安全性从「会话有效」降级为「必须重新登录」。

## 4. 参考答案

1. 状态 200 ≠ 源活着：反爬页（36kr/zhihu）返回 200 但 0 items，超时（NYT/BBC）是死源。实测要用应用同链路（Node fetch 解压），curl 不带 --compressed 收 gzip 字节 grep 不到 item 是假阴性。预置话题是运营者帮你找源（B 路线无搜索引擎），入库标准是拉到 items 实数，最终 8 话题只进 6 源。

2. 密码都丢了，旧 session 等于「未经身份确认的持续信任」，不可信。吊销后用户必须走新密码重新登录，重置码也单次消费，防重放和双花。

3. 码与用户名绑定→拿别人的码改不了别人的号；先验后消费→弱密码/格式错被拒时码不烧掉，防止被试探耗光；串行队列原子窗→「验证+消费」必须原子，防并发双花。同构于邀请码池的 create/list/reset 三函数。

4. 升序时最新日期在 picker 底部，用户每次都要翻到底才看得到最新数据，反直觉。改 b.localeCompare 倒序 + 默认 dates[0] 后，默认值就是最新，打开即最新。localeCompare 保证字符串日期按字典序稳定可比。

5. 401（未登录）和 429（限流）对用户都是「没登上」，断言按业务语义收（非 200 即失败）而不是区分错误码；uni-input 的 placeholder 是自绘元素、不落原生 input 属性，Playwright 按 placeholder 定位必失败，要按卡片位置定位元素。
