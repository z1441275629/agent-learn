## 2. 核心知识讲解

### A. LangGraph 线程模型：身份、快照、分叉与回滚

**是什么**：LangGraph 的「会话」不是 agent name，而是 thread_id：checkpointer 按 `cfg.configurable.thread_id` 找历史，name 只是给 LangSmith 看的标签。删了 .s6-data 库、同 thread_id 再跑，又攒出新历史——看起来「会话还在」其实是身份键没换。

**为什么**：graph 每次执行把每一步（superstep）的状态序列化后写入 checkpointer。MemorySaver 也不存对象引用，serde.dumpsTyped 成 JSON 字符串落 Map，读时反序列化新对象——所以「原地改 reducer 污染历史」是伪命题，快照写时已冻结成字节拷贝，原地改的是活的 channel 对象，碰不到历史。

**怎么用**：API 单线程视角用 getStateHistory 按 step 回看；跨线程血缘只有 SQL 直读 checkpoints 表的 parent_checkpoint_id 才能重建（fork 的血缘跨 thread，API 单线查询看不见）。fork = 选中间 checkpoint_id + 新 thread_id 长出一条新线（原线 Rust、分叉线 Go 双线对比）；reset = 同 thread_id + 旧 checkpoint_id 回滚，抹掉旧未来。分叉和回滚都显示为血缘树上的树枝。

**和什么相关**：与 pa 的 sessions 业务层快照对照——框架层每 superstep 自动快照，业务层要自己决定「什么算一个会话里程碑」；Store（跨线程共享记忆）vs thread state（线程内上下文）是两层生命周期。

### B. 中间件护栏与 ToolMessage|Command 双形状契约

**是什么**：deepagents 的 createAgent 通过 wrapToolCall 包装工具调用，可在工具执行前后注入逻辑——这是「框架没内置护栏、middleware 补齐」的宿主（对照表第 7 行实证）。S6 的 reviewBreaker 就挂在 wrapToolCall 里：拦 task→critic 的调用，req.state.criticCalls 计数（增量 1、reducer 求和），≥2 后拒发第 3 次调用、注入一个熔断令牌 ToolMessage 让模型自己收尾（降级交付最后一稿，对照 pa 写手段熔断=降级交付）。

**为什么**（关键坑）：
- handler 的返回值不只是 ToolMessage：deepagents 内置 task 工具跑完子代理返回 Command（update 带 files 合并 + 结果 ToolMessage，源码 returnCommandWithStateUpdate）。护栏写死 messages:[res] 把 Command 当消息塞数组 → "Unable to coerce message from array"（用户实测，critic 第 1 次审校完成后在合并处炸）。修法 = 两种形状透传：Command 展开 update 叠加计数、ToolMessage 才包一层。
- 拒发也必须补写 tool_call_id 回执（#72 教训），否则悬空 tool_call 让图卡死。
- 计数通道挂 stateSchema，随线程持久化——所以 breaker 强制新线程，否则旧线程历史计数直接顶满阈值；approve 自动跟 last-thread（读方绝不写，标记只有一个写方），否则审批打到旧会话。

**怎么用**：演示模式 = 任务核心主张与知识库 notes 故意冲突，critic 对照永远 FAIL、锁死主张不许改，逼出熔断路径。对照手写图（条件边+两态分离，s3 已建）与 deep agent（无审校节点→middleware 层）——同一个护栏、两种宿主。

### C. 护栏的宿主决定可测性（S6 breaker 三轮演化收官）

**是什么**：同一个「审校 2 次未过熔断」护栏，在两个宿主里可测性完全不同。手写 StateGraph（s3 composite）：熔断是条件边里的计数判断（`revisions>=2` 出图）——**拓扑强制**，测试可确定性构造打回路径，不依赖模型行为。deep agent（模型循环）：循环在主 agent 的 ReAct 里，「再叫一次 critic」是模型的决定，没有审校节点可挂条件边——护栏只能落在 wrapToolCall 执行层，**触发依赖真实的病态循环**。

**为什么**（三轮逃逸实录，为什么演示任务压不出熔断）：
- v1 留了口子：critic 把「主张是硬性要求」当给定条件，自己给出折中（保主张改措辞）→ 两轮真 PASS。
- v2 攻击诚实性：让交付物成为与知识库相反的假话 → agent 查完 notes 直接拒单（grounding 生效，正验收，但循环根本没启动）。
- v3 攻击职责边界：塞一条用户自述的无出处数据、锁死不许删 → agent 如实标注「内部统计无出处」，critic 认为如实标注的断言不算违规 → 一轮 PASS。

**怎么讲（面试）**：护栏演示的对抗设计要攻击护栏的**触发条件**（无产出循环），不是 agent 的**人格约束**（诚实性）——压过对齐性才能演示的护栏，演示本身已经失真。诚实 agent + 职责 critic 会合作 PASS 任何如实标注的内容；熔断在生产里只拦真病态。验证状态如实记录：✓护栏非侵入 ✓双形状透传 ✓grounding 正验收，✗熔断分支未真实触发（代码级审查置信）。

**和什么相关**：与 #74 静默空同属「验证状态如实记录」纪律——没踩到的分支不许说验证过。

### D. 检索质量评估与静默空（S7 RAG）

**是什么**：官方 retrieval 路线三件套——splitter（RecursiveCharacterTextSplitter 递归分隔符 500/50）、vectorstore 包装（Chroma.fromDocuments 一步建集合+批量嵌入+入库；`asRetriever({k})` 是策略位）、BM25Retriever（内存建索引即用，无索引依赖）。评估 = LangSmith `evaluate()`：dataset（8 例，实体/字面与改述各半——#63 的两类查询形态，只测字面会高估）+ target（retriever.invoke）+ 评估器（hit@3：期望文档进没进 top3；MRR：进了排第几，`1/(idx+1)`）。

**为什么**（两个实锤坑）：
- **评估器形状**：langsmith 0.9 的 evaluators 要**裸函数** `(args)=>{key, score}`——传 `{key, evaluate: fn}` 对象会走废弃 RunEvaluator 分支（找 .evaluateRun 方法）报 `evaluator is not a function`。数据取位：`args.outputs`=target 返回值，`args.referenceOutputs`=example 参考输出。
- **静默空（#74）**：`fromExistingCollection` 是 getOrCreate 语义——未 ingest 直接 ask，静默建空集合、向量查询静默返回空，**0 分实验照常跑完**。定位靠对账：`col.count()=0` 即实锤。

**怎么用**：改述+实体混合查询两路失败模式不同——向量输给「同类段落难分」（语义都相似，对象错了）；BM25 输给「唯一存活 token 定去向」（空白分词下英文 token 是救命稻草）——这是混合检索的互补机理。

**和什么相关**：pa 手写 upsert+对账自愈（kb.json 唯一事实源、索引是可重建缓存）vs 官方包装没有这层；retriever 抽象让「向量/BM25/混合」成为可替换策略位，#63 的实测选型在策略位里完成。

## 4. 参考答案

1. 会话身份 = thread_id：checkpointer 按 cfg.configurable.thread_id 找历史，name 只是 LangSmith 标签。删库后同 thread_id 再运行，新历史又累积（实测库中单线程 57 checkpoint），观感上「会话延续」。干净做法是 --fresh 换新 thread_id（不动工作区），比删 .s6-data 干净。

2. fork：从某中间 checkpoint_id 配新 thread_id 长出新线程线，原线继续走，两条线并行对比；reset：同 thread_id + 旧 checkpoint_id 回滚，把旧未来抹掉重走。血缘树靠 SQL 直读 checkpoints 表 parent_checkpoint_id 重建——API 的 getStateHistory 是单线程视角，跨线程血缘看不见，SQL 才是全图。

3. FilesystemBackend 的 resolvePath 在 virtualMode 默认 false 的 legacy 模式下，绝对路径原样放行：模型 ls 猜绝对路径直接列宿主机 E 盘；skills:['/skills/'] 在 Windows 是盘根相对路径 → 解析成 E:\skills → 技能没注册（验收假阳性：任务完成≠技能机制走通）。virtualMode:true 才强制虚拟绝对路径 + 圈禁，.. 穿越/出界抛错。教训：backend 根目录参数先问「是不是沙箱」，跨平台虚拟路径必须显式开虚拟模式。

4. 挂在 wrapToolCall（deepagents 的中间件机制）：req.state.criticCalls 计数（ReducerValue 增量语义，reducer 求和），≥2 拒发第 3 次、注入熔断令牌 ToolMessage 带降级规则让模型收尾。handler 返回值是双形状契约：deepagents 内置 task 工具跑完子代理返回 Command（update 带 files 合并 + 结果 ToolMessage），写死 messages:[res] 会把 Command 当消息塞数组 → Unable to coerce message from array（用户实测在合并处炸）。修法：Command 展开 update 叠加计数，ToolMessage 才包一层——护栏必须是无损透传层。拒发也要补写 tool_call_id 回执防悬空；计数走 stateSchema 随线程持久化，breaker 强制新线程防旧计数顶满；approve 跟 last-thread 防审批打到旧会话。

5. 工具 return Command goto 不带 update → ToolMessage 丢失 → 悬空 tool_call → 接手 agent 空回答（#66 放大版）。goto 只搬控制权，update 才搬干净线程（含结果消息）。且交棒消息要面向接手方写角色指令（「你现在是XX + 先找未处理问题 + 别重复」），不是写给发球方的收条——交棒消息是协议不是日志，写给谁看决定 handoff 质量（PITFALLS #72）。billing 答发票 → 交棒 → tech 以正确角色答键盘急救，最终消息清单 4 条干净收场。

6. 手写图：熔断是条件边计数判断（revisions>=2 出图），拓扑强制——测试可确定性构造打回路径，不依赖模型。deep agent：循环在 ReAct 里，「再审一次」是模型决定，没有审校节点，只能挂 wrapToolCall 拦 task→critic 调用——触发依赖真实病态。三轮逃逸：v1 critic 自由裁量给折中 PASS；v2 攻击诚实性——agent 拒写假话（grounding 生效但循环没启动）；v3 无出处数据被如实标注，critic 认为如实标注不违规。结论：护栏演示要攻击触发条件（无产出循环）不是人格约束——压过对齐性才能演示的护栏，演示已失真；**护栏的宿主决定可测性**。

7. 静默建空集合+查询静默返回空：getOrCreate 语义，不报「集合不存在」。0 分实验照常跑完，没有异常可抓——表象是「向量没结果」，锅在创建语义。定位靠对账：col.count() 查集合条数，0 即实锤。原则：检索实验先验数据在位（count 对账再跑），静默空比报错难排查一个量级——报错自带方向，静默空只有 0 分。

8. BM25Retriever 默认空白分词：中文没空格，整句被切成极少的大 token，词项匹配几乎失效——检索质量的地基在分词（pa 自写 CJK 二元组的动机，#63 的隐含实验条件）。英文 token 自带空格边界存活，混中文查询时英文词成为唯一可匹配信号、决定 BM25 的召回方向。两路实测：向量输给同类段落难分（语义都相似对象错了），BM25 输给唯一存活 token 定去向——互补机理，混合检索的动机。

9. dataset：8 例实体/字面与改述各半——覆盖 #63 的两类查询形态，只测字面命中会高估检索质量；语料是自己的学习文档，source 元数据即命中标签、答案可回查（eval 标签天然可信）。评估器：hit@3 = sources.includes(expected)（期望文档进没进 top3）；MRR = 1/(idx+1)，没进记 0（进了排第几）。坑：langsmith 0.9 的 evaluators 要裸函数 (args)=>({key, score})——传 {key, evaluate:fn} 对象走废弃 RunEvaluator 分支报 evaluator is not a function；target 返回值从 args.outputs 取、参考答案从 args.referenceOutputs 取；experimentPrefix 决定 UI 里的实验名。
