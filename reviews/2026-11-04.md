## 2. 核心知识讲解

### ① 写入工具的「确认门」与 fail-closed 安全模型

**是什么**：agent 要调写入类工具（写记忆、写笔记）时，不能默默执行——先通过 SSE 给用户弹一张确认卡，等人批准；批准前一切默认拒绝。

**为什么**：
- LLM 可能自主决定去改持久状态，这是有副作用的动作，必须人在环（human-in-the-loop）
- 不能只靠模型"保证不滥用"，机制上就要强制

**怎么用**（四条 fail-closed 边界）：
- 无门（工具没注册权限通道）→ 拒绝
- 门抛错 → 拒绝
- 用户拒绝 → 拒绝
- 超时 / 连接断流 → 拒绝（怕的是断流后模型误以为已批准继续执行）

**和什么相关**：与「本会话内总是允许」（仅内存态不落盘不跨会话，防止疲劳点卡）配合；是浏览器 click/type「写侧过确认门」的同款机制。

### ② 浏览器工具闭环：read → act → read

**是什么**：让模型能真正操作浏览器，而不是只读网页。三步闭环：
1. `browser_read`：打开页面，等 JS 渲染完取正文，同时给每个可操作元素打 `data-pa-ref` 编号（≤80 个可见才给）
2. `browser_click` / `browser_type`：按编号操作（写侧过确认门）
3. 页面变了 → 旧编号作废 → 报错让模型重读，**绝不猜**

**为什么**：只读浏览器（v1）是第一步，但真正的 agent 要能点按钮、填表单。编号体系让模型有稳定的"抓手"，不靠瞎猜元素。

**关键坑**：ToolDef 加 describe 把 `{ref:3}` 解析成卡面人话 `[3] button「点我」`；页面变化后编号失效必须报错逼模型重读，不能让它凭记忆猜（否则会点错）。

### ③ 服务端转写为何不用 MediaRecorder（PITFALLS #44）

Chrome 的 MediaRecorder 只产 `webm/opus`，而 GLM-ASR 的「OpenAI 兼容」只指**协议**兼容，**不指文件格式**——它只收 WAV。所以弃 MediaRecorder，改 **Web Audio 采 PCM + 手写 PCM16 WAV**（44 字节头纯函数，AudioWorklet 走 Blob URL 注入、过零增益防回放、16k 采样）。

**通用教训**：兼容性要验证到「文件格式」这一层，协议兼容 ≠ 格式兼容；E2E 补「上传的是 wav」断言，防止 mock 宽容掩盖格式假设。

## 4. 参考答案

1. **四条边界**：写入是有副作用的持久改动，人必须在环。无门说明机制没提供授权通道；门抛错是机制故障；拒绝是用户行使否决权；超时/断流最危险——断流后模型可能误以为已批准就继续执行，所以一律 fail closed（默认拒绝）才安全。任何一环不满足，动作不执行。

2. **让模型重读**：编号是快照时刻的"临时地址"，页面变化后 DOM 结构可能完全不同，旧编号会指向错误元素甚至不存在的东西。如果允许猜，可能点到完全不相干的元素造成破坏性操作。报错逼重读是**用机制防模型幻觉**，成本是一次 read，收益是杜绝错点。

3. **兼容陷阱**：「OpenAI 兼容」指协议层（HTTP、路由、鉴权），不保证文件格式。GLM-ASR 只收 WAV，MediaRecorder 只产 webm/opus，格式不符直接 404/502。教训：兼容性要验证到最底层的数据格式，不能停在"协议对了"；测试要断言真实格式（E2E 查"上传的是 wav"），否则 mock 宽容会掩盖真实环境失败。

4. **并发策略**：按工具副作用分类——只读工具（get_time/search_kb 等）无副作用，可并发，墙钟取 max 完成时间；写入工具（remember/add_note 等）有副作用且要过确认门，必须串行，确认卡一张一张出，且后面的决定能看到前面的结果（"本会话总是允许"顺序生效）；喂回模型的 tool 消息严格按 tool_calls 原始顺序拼接（并发完成序会乱，而 API 契约要求原序），探针 Q16 钉死这三性质。

5. **确认卡串行**：同一个 tool_calls 批次里如果有多个写入调用，它们不能同时出卡（否则用户在 N 张卡里乱点，状态会乱）。实现上写入工具串行过门，第一张卡 ask→ok 后才出第二张 ask→ok；这样"本会话总是允许"会顺序生效，后面的决定能看到前面批准的结果，语义一致、无竞态。E2E D5 双写一卡一答验证。
