# Planner-Executor 范式落地：从概念到编排的实战避坑记录

如果你做过稍微复杂一点的 LLM Agent，大概率会遇到同一个问题：任务太长、工具太多，模型一轮推理根本跑不完，甚至跑着跑着就偏了。这时候，一个常见的解法是把「思考」和「动手」分开——先用一个规划器把任务拆成步骤，再让执行器逐步完成。这就是 Plan-and-Execute 范式，而它的角色分工，就是我们今天要聊的 Planner/Executor。

概念听起来不复杂，但真正落到代码里，你会发现细节比想象中多得多。这篇文章从一个真实仓库里的「写博客编排」模块出发，记录 planner-executor 落地时的几个关键决策：角色怎么分、路由怎么触发、成本怎么控制、幻觉怎么压、异常怎么归因。这些经验不是来自教科书，而是来自一次次的提交记录和源码调试。

## 从概念到家族：Planner/Executor 与它的伙伴们

Planner/Executor 的核心思想很简单：**先把任务拆成步骤，再逐条执行**。它特别适合长任务场景，比如「写一篇技术博客」这种需要取材、审校、成稿、再审校的多阶段工作。

在概念上，这个范式还有一个家族。Handoff 指的是任务控制权的交接——一个子 agent 干完活，把控制权交给下一个；Supervisor 则是一个主管调度者，负责协调多个子 agent 的分工。Planner/Executor、Handoff、Supervisor 本质上都在解决同一个问题：**如何让多个 LLM 角色协作完成一个复杂任务**，只是侧重点不同。

但光理解概念是不够的。真正落地时，你需要面对的是：角色之间怎么传数据？谁来审校？审校不过怎么办？预算怎么限制？这些问题，仓库里的模块 16 给了我们一个很具体的答案。

## 真实落地：模块16 的 composite 编排

模块 16 是一个「写博客编排」的 composite 模式实现。它不是一个简单的 planner → executor 两步走，而是一条完整的角色链：

1. **研究员（只读子 agent）**：负责取材，只能读，不能写。
2. **审校①**：对研究结果做第一轮评审。
3. **写手**：基于审校过的研究结果成稿。
4. **审校②**：对成稿做第二轮评审。

这个链路有一个很关键的设计：**修订熔断 ≤2 轮**。也就是说，写手写完初稿后，如果审校②发现问题，最多只能打回重写两次，超过就停止。这防止了「审校→重写→再审校→再重写……」的死循环。

除了熔断，还有两套防护措施：

- **成本护栏**：限制工具调用轮数和总调用次数，防止 agent 在某个环节过度探索。
- **abort 三件套**：支持随时中断编排流程，防止意外情况下继续烧钱。

这三样东西合在一起，构成了防烧钱、防死循环的基本盘。实际做 agent 应用时，这三点缺一不可——没有熔断，模型可能永远在自我修正；没有护栏，一次小任务可能烧掉你半个月的 token 预算。

## 路由与成本：零 token 识别和 ReAct 的隐形开销

在编排启动之前，首先要回答一个问题：**用户的消息到底要不要走这个多角色流程？**

仓库里的做法很朴素：用规则触发，实现 **零 token 识别**。也就是说，在调用任何 LLM 之前，先用正则把请求拦一遍。

问句先拦：包含「怎么/如何/吗/？」等标记的，直接不走博客编排。

写博客意图的匹配正则长这样：

```regex
写|生成 .{0,25} 博客|技术文章
```

这个正则是匹配「写……博客」或「生成……技术文章」这类模式。这里有个有趣的细节：间隔长度最初是 **15**，后来放宽到了 **25**。原因是长主题名会把「写」和「博客」之间的距离撑到 **21 个字符**，导致正则匹配失败，请求静默降级成单 agent——用户明明想写一篇博客，却只启动了一个研究员，后面审校、写手全都没触发。

这个坑提醒我们：**规则触发虽然便宜，但阈值必须贴合真实输入分布**。如果你用了间隔上限，最好拿真实的用户请求跑一遍回归，否则漏触发时，系统不会报错，只会静默地走错流程。

成本方面，另一个大坑来自 ReAct 范式的实现方式。你可能会以为，Agent 思考贵是因为「想得多」，但实际情况是：**ReAct 每轮都会重发全部历史结果**。6 次工具调用，就要把之前的每轮结果都塞进 prompt 里，一轮一轮累积，最后烧掉 6 万 prompt token——注意，这不是「思考贵」，是「记忆贵」。

对应的修法也很直接：

- **源头截断**：研究员段的 `maxResultChars` 从 9000 收紧到 3000，减少进入上下文的原始材料。
- **机械闸收紧**：`maxRounds` 从 4 降到 3，`maxCalls` 从 6 降到 4。

这两招的本质是：**与其让模型自己学会节省，不如在系统层面把它能花的钱限制死**。对于工具调用型 agent，prompt 的历史累积开销是指数级的，越早截断，省得越多。

## 审校与归因：压幻觉的关键和 catch 的陷阱

多角色编排里，审校层是**压幻觉**的关键防线。模块 16 里，审校结论通过 `parseCriticVerdict` 解析，有两个特点：

1. **首行锚**：解析时锚定输出的第一行，避免被后续的冗长解释干扰。
2. **fail-closed**：解析失败时默认判定为「不通过」，而不是放行。

审校提示词分研究、写作两段，各自有不同的评审重点。其中，**忠实性判据**特别值得关注——它明确点出了两处盲区：

- 代码/命令示例里的具体值（路径、文件名、日期、数字）必须要有简报依据。你不能让写手凭空编一个 `maxRetries=5`，即使这个值看起来很合理。
- 笼统的技术表述要与简报里的实际机制一致。比如简报说 maxRounds 从 4 降到 3，你就不能写成「增加了轮数限制」。

这两条规则对写博客这种场景尤其重要，因为 LLM 在生成代码示例时，很容易「顺手」填一个合理的数字——但对读者来说，这就是错误信息。

最后一个值得一提的坑，是编排内部 catch 的**归因陷阱**。在非流式单发调用场景下，如果请求被 abort，会抛出一个 `AbortError`。这时如果你在 catch 里不做区分，直接当成普通错误处理，就会把「用户主动取消」误标成「系统错误」。

正确做法是：

```javascript
catch (err) {
  if (err.name === 'AbortError' || signal.aborted) {
    // 按 aborted 归因，让 chat 以 interrupted 状态落盘
  } else {
    // 真正的错误处理
  }
}
```

先查 signal 再谈错误，按 aborted 归因，让对话以 `interrupted` 状态落盘，而不是 `error`。这不仅是日志好看的问题，还影响后续的恢复逻辑——interrupted 的任务可以续跑，error 的任务往往需要人工介入。

## 总结

Planner-Executor 不是一个遥不可及的概念，它就是你写博客编排时那一条「研究员→审校→写手→审校」的角色链。回看整个落地过程，有几个经验值得带走：

- **概念要落地，必须配合工程护栏**：修订熔断、成本上限、abort 三件套，缺一个都可能让系统失控。
- **路由触发要贴近真实输入**：正则阈值不是拍脑袋定的，长主题名会把间隔撑到 21 字符，阈值 15 就是会漏。
- **成本大头是历史累积，不是思考本身**：ReAct 每轮重发全部历史，截断源头参数比限制思考次数更治本。
- **审校要 fail-closed，判据要具体**：首行锚 + 默认不通过，具体值必须溯源，笼统表述必须与机制一致。
- **catch 里先看 signal，再谈错误**：abort 不是 error，归因错了，后续恢复逻辑都会错。
