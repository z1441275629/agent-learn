# 02 · RAG 与检索

> 覆盖：链路全貌 / chunking / 嵌入与向量库 / 混合检索 / rerank / 评估 / 微调 vs RAG 选型。RAG 是 AI 应用岗笔试面试最高频模块，没有之一。

### Q1. 画/说一遍 RAG 的完整链路。【必背★】

**背诵版**：分离线索引和在线问答两条链。**离线**：文档加载 → 清洗 → 切分（chunking）→ 嵌入（embedding）→ 入库（向量库，带元数据）。**在线**：用户 query → （改写）→ 检索（向量/BM25/混合）→ 重排（rerank）→ 取 top-k → 拼进 prompt（附引用来源）→ 生成 →（忠实性校验）。每一步都是可独立失效的环节，**排查 RAG 问题必须分段定位**：先看检索有没有召回（不是模型瞎答），再看生成有没有忠实（召回了但没用上）。

**追问**：Q：为什么生成前要重排？→ 见 Q6。Q：元数据有什么用？→ 过滤（按时间/来源/权限）+ 溯源引用，生产 RAG 没元数据等于裸奔。

### Q2. chunking 怎么切？大小怎么权衡？【必背★】

**背诵版**：核心矛盾是**检索粒度 vs 语义完整性**：切太小，单块语义破碎、召回命中了也读不懂；切太大，单块信息密度低、top-k 预算被浪费、且稀释 prompt。经验起点：几百 token 一块、相邻块留 10~20% 重叠防边界切断语义。更重要的原则是**结构感知切分**：按标题/段落/代码块等天然边界切，优于机械定长；表格、FAQ 这类内容整块保留别切碎。切分策略没有银弹，**要靠评测集对比调**，不是拍脑袋。

**追问**：Q：中文切分有什么特殊点？→ 中文没有空格分词，机械切分更容易切断词组，更要依赖标点/段落边界。Q：parent-child 检索是什么？→ 用小块做检索命中、返回其父块给模型，粒度和完整性两头兼顾。

### Q3. 嵌入模型是什么？怎么算相似度、怎么选型？【必背★】

**背诵版**：嵌入模型把文本编码成定长向量，**语义相近的文本在向量空间中距离近**。相似度算余弦（夹角），生产实现常归一化后用点积。选型看：MTEB 类榜单的检索子项成绩、**向量维度**（维度高表达强但存储和算力贵）、支持语言（中文要选中文优化过的）、上下文长度、推理成本（自部署还是 API）。工程要点：**query 和文档必须用同一个嵌入模型**，换模型必须全量重建索引；相似度阈值要用自己的数据标定，不同模型的分数分布不可比。

**追问**：Q：余弦相似度 0.8 算相关吗？→ 没有普适答案，分数分布随模型和数据集变化，要拿自己的正负样本对画分布定阈值。Q：排版格式影响相似度吗？→ 会，同一内容排版变了相似度可能跨阈值（实测踩过），入库前统一清洗格式。

### Q4. 向量库怎么选？什么规模用什么方案？【进阶】

**背诵版**：三档。① **进程内/嵌入式**（如 sqlite-vec、hnswlib、内存数组）：十万级以下、单机、零运维——**小规模别上重型库，余弦相似度全量扫都够快**；② **专用向量库**（Milvus、Qdrant、Chroma server 等）：千万级、需要分布式和高级索引（HNSW/IVF）；③ **现有数据库扩展**（pgvector、Redis）：数据本来就在库里、想少加一个组件。选型真实考量：规模、元数据过滤能力、混合检索支持、运维成本——**很多人高估了自己需要的规模**，百万级以下嵌入式方案加内存索引完全够。

**追问**：Q：HNSW 是什么？→ 分层可导航小世界图，近似最近邻索引，查询快内存换精度，是向量库主流索引。Q：不走向量的场景？→ 关键词/精确匹配为主的库（错误码、API 名），BM25 更准还免费。

### Q5. 为什么单路向量检索不够？混合检索解决什么问题？【必背★】

**背诵版**：向量检索擅长**语义泛化**（「怎么省钱」→「成本优化」能召回），但对**精确符号**弱：专有名词、错误码、API 名、型号这些 query，嵌入容易糊掉，反而 BM25 关键词匹配精准。反过来 BM25 不懂同义改写。所以生产标配**混合检索**：BM25 + 向量两路各出候选，再用 RRF（倒数排名融合）或加权融合合并——互补且实现便宜。我的实践里还踩过：中文 BM25 要处理分词（二元组/n-gram 是无词典方案），否则关键词路也是浆糊。

**追问**：Q：RRF 怎么算？→ 每路按排名贡献 1/(k+rank)，k 常取 60，无需分数归一化——不同路的分数不可直接比，排名融合绕开了这个问题。Q：实体查询向量检索差怎么办？→ 实体走关键词/结构化查询，语义走向量，路由或融合。

### Q6. rerank 是什么？为什么检索后还要重排？【必背★】

**背诵版**：召回用的嵌入是 **bi-encoder**（句向量离线算好、在线只比距离，快但粗）；rerank 是 **cross-encoder**（query 和文档拼一起进模型算相关性分，准但每对都要跑一次推理，慢）。所以工程上分层：**召回层用便宜的方法从海量里粗筛 top-50~100，重排层用贵的模型精排取 top-3~5**——精度和成本的平衡结构。效果上 rerank 对「召回对了但排序乱」的问题提升明显，是 RAG 调优性价比最高的一刀之一。

**追问**：Q：为什么不直接用 cross-encoder 检索全库？→ 每对文档一次推理，全库是 O(N) 次模型调用，线上不可承受。Q：没有 rerank 模型怎么办？→ LLM 打分重排（贵）或先靠混合检索融合排序顶着。

### Q7. query 改写和多查询扩展值得做吗？【进阶】

**背诵版**：用户的原始 query 往往不是好的检索 query。常见增强：① 改写（口语→规范、补全指代——多轮对话里「它怎么部署」要结合历史改写成完整 query）；② 多查询扩展（一个 query 生成多个变体分别检索再合并）；③ HyDE（让模型先生成假设答案，拿答案去检索——答案和文档的向量空间更近）。**代价是多一次 LLM 调用的延迟和成本**，值得与否看场景：多轮对话指代消解几乎必做，HyDE 类只在召回率实在上不去时上。还有个反面：**寒暄级短 query 不该触发检索**，白花钱还稀释上下文——加意图判断挡一道。

**追问**：Q：怎么判断该上 query 改写？→ 评测集里「检索 recall 低但人工改写 query 后能召回」的样本多，就值得。

### Q8. RAG 系统怎么评估？【必背★】

**背诵版**：分两层测，别只看端到端。**检索层**：recall@k（该召回的文档有没有进 top-k）、MRR（正确文档排多前）——用标注好的 query→文档对做评测集。**生成层**：忠实性（答案是否真有检索材料依据，防「检索对了但模型自由发挥」）、相关性（答没答到点）、引用正确性。端到端再配任务级评测（如问答准确率）。方法论要点：**先分层定位再优化**——端到端分数低，先查是检索没召回（改切分/检索策略）还是生成不忠实（改 prompt/温度/忠实校验），对症下药；每次改动跑同一评测集对比，没有评测集的 RAG 调优是玄学。

**追问**：Q：忠实性怎么自动评？→ LLM-as-judge：给判官「材料+答案」问每个论断是否有依据，注意判官本身的偏差（锚定判定标准、低温度）。

### Q9. 微调、RAG、prompt 工程怎么选？【必背★】

**背诵版**：三者解决的问题不同：**prompt 改指令遵循，RAG 改知识，微调改行为模式**。知识频繁更新、需要溯源、私有文档问答 → RAG；输出风格/格式/领域行为模式要固化 → 微调（但先穷尽 prompt + few-shot，微调是重武器）；指令没吃透 → prompt 工程，永远从这开始。常见组合是 RAG 打底 + 小规模微调调风格。选型时算账：微调有数据准备、训练、评估、维护成本，且知识更新要重训；RAG 增删文档即时生效。**默认序：prompt → RAG → 微调**，倒着来基本是烧钱。

**追问**：Q：微调能让模型「记住」公司知识吗？→ 能记住一部分但不可靠且不可溯源，知识注入的正确位置是 RAG，微调留下的应该是行为不是事实。

### Q10. RAG 常见失效模式有哪些？怎么排查？【进阶】

**背诵版**：常见五种：① **检索空/漏**——query 和文档语言不匹配、切分破坏语义、嵌入模型不适合该域；② **排序乱**——召回对了排不进 top-k，上 rerank；③ **上下文稀释**——top-k 塞太多、相关信息被淹没，减 k 或压缩；④ **不忠实**——材料有但模型无视，prompt 强制「仅根据材料」+ 忠实校验；⑤ **数据脏**——入库内容过期/重复/格式混乱，检索层无解。排查动作固定：拿失败 case 沿链路看——**检索结果先于模型输出看**，多数「RAG 不准」其实是检索层的事。

**追问**：Q：最容易被忽视的环节？→ 离线数据质量（清洗/去重/更新机制），大家都在线调参，脏数据进啥都白搭。

### Q11. Agentic RAG 和 GraphRAG 是什么？什么时候用？【进阶】

**背诵版**：传统 RAG 是固定流水线（必检索→必生成）；**Agentic RAG 把检索变成 agent 的工具**——模型自主决定查不查、查什么、查几轮：明确知道答案就不查（省成本），一次没查够可以改写再查（多跳）。代价是引入 agent 的不确定性和延迟，适合开放域复杂问答；简单 FAQ 固定链路更稳。**GraphRAG** 在向量索引外再建实体关系图，多跳问题（「A 的合作方的竞品是谁」）沿图遍历比向量检索准，代价是建图和维护成本高。**判断标准：多跳/关系型问题占比高才值得上，否则是过度设计**。

**追问**：Q：你的项目怎么选的？→ 个人知识库（百级条目、均匀轮换才是真需求）用 BM25 全量内存检索+自主检索双路线，没走向量也没上图——规模决定选型。

### Q12. 说一个你亲手做过的 RAG 系统，以及两个最深的坑。【必背★】

**背诵版**：个人工作台的知识库检索：本地 BM25（中文无词典用二元组分词）+ 元数据，**双路线**——固定注入（每轮带基础知识）与模型自主检索（`search_kb` 工具，模型判断需要才查）并存，寒暄级 query 不触发检索。坑一：**实体/精确查询的向量检索是浆糊**——人名、错误码这类 query 嵌入糊掉，关键词路才准，这就是我坚持混合检索的实证来源。坑二：**格式变化跨阈值**——同一内容排版变了相似度就跨过查重阈值，去重逻辑不能只靠相似度分数，要配合稳定去重键（如内容哈希）。

**追问**：Q：为什么不用向量？→ 库小（百级），均匀轮换、错题优先才是真实需求，检索质量不是瓶颈——**选型看需求不是看技术热度和简历好看**。Q：如果库到十万条？→ 上嵌入+混合检索+rerank 标准分层，链路位置都留好了。
