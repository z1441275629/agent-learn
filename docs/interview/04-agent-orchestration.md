# 04 · Agent 编排与 LangChain/LangGraph

> 覆盖：ReAct / Planner-Executor / 多 Agent 拓扑 / StateGraph / checkpointer / interrupt / 框架选型。这章是把「会调 API」和「会做 Agent 系统」分开的地方。

### Q1. ReAct 是什么？循环怎么终止？【必背★】

**背诵版**：ReAct = Reasoning + Acting 交替：模型思考→调工具→看结果→再思考……直到产出最终答案。终止条件三道闸：① **自然终止**：模型返回纯文本不再发起调用；② **预算闸**：轮次上限（maxRounds）/单轮调用上限（maxCalls）超限后**机械强制收敛**——去掉 tools 再调一次逼它出文字结论，不靠提示词求它收尾；③ **异常终止**：不可恢复错误走降级路径。**「机械终止闸」是工程要点**：提示词里的「请及时停止」对失控模型没有约束力，代码层硬闸才有。

**追问**：Q：为什么模型会停不下来？→ 工具结果质量差它反复重试、或陷入「再查一次」循环——正是硬闸存在的理由。Q：ReAct 每轮都重发全部历史，成本怎么算？→ 累加的，这是 ReAct 最大的成本结构问题（见第 6 章 Q1）。

### Q2. Planner-Executor 和 ReAct 单环有什么区别？什么时候需要规划器？【必背★】

**背诵版**：ReAct 是**边走边想**（每轮基于最新观察决定下一步），Planner-Executor 是**先想好再走**：规划器一次产出步骤表（严格 JSON，步骤数受控），执行器逐步执行，步骤间传递产物摘要。选择判据：**任务可分解且步骤间耦合低**（研究→写→审这类流水线）用规划，收益是全局视野和步骤可控；**探索型任务**（排障、开放检索）路径依赖中间发现，提前规划反而是幻觉步骤表。工程必备件：规划失败 fail-closed 回落单 agent，执行失败不拖垮全局。**两者不互斥**——复杂系统常见外层规划+局部 ReAct。

**追问**：Q：步骤间怎么传递上下文？→ 不传全量，传「仓库产物+结构化摘要」，防上下文膨胀。Q：步骤表锁多长？→ 有上限（如 ≤4 步），长了说明该拆子任务或任务本身不适合规划。

### Q3. 什么时候值得拆多 Agent？收益和代价各是什么？【必背★】

**背诵版**：收益三个：① **上下文隔离**——每个 agent 拿干净上下文，不被全局历史污染（子 agent 只带任务说明，返回结果摘要）；② **角色专注**——不同角色配不同模型档位/温度/工具面（审校温度低、写手温度高）；③ **并行**。代价三个：① **token 成本翻倍**（每个 agent 独立上下文+编排层开销）；② **交接失真**（agent 间传摘要必有信息损失，链式审校验交接一致性验不了源头正确性）；③ **调试复杂度**（错误归因跨 agent 链路）。**判据：单 agent 上下文已经互相干扰、或角色确实需要不同配置时才拆；为了「多 Agent」标题拆是伪需求**。

**追问**：Q：最小可行的多 agent 是什么形态？→ 主 agent + 专项子 agent（只读取材/单一职责），主 agent 统一决策。

### Q4. 多 Agent 的两种基本拓扑：supervisor 和 handoff？【必背★】

**背诵版**：**supervisor（主管模式）**：中心节点持有全局状态，把任务分派给 worker、收结果、决定下一步——控制力强、全局视野好，代价是主管是瓶颈和单点。**handoff（交接模式）**：agent 之间直接移交控制权（A 干完叫 B），无中心——去中心化、链路灵活，但全局状态要靠传递协议维持、易失控。选型：**流程已知、需要统一审计**用 supervisor；**对话式流转**（客服转接、专家接力）适合 handoff。共同工程点：交接时要给接手方完整交接语义（谁、干了什么、需要你干什么），以及**终止权永远要有确定性的持有者**（拓扑层面防死循环）。

**追问**：Q：LangGraph 里各怎么落？→ supervisor=中心节点条件路由；handoff=每个 agent 一个「转交」工具，goto 指定接手方（注意 ends 白名单与面向接手方的消息语义）。

### Q5. agent 之间交接上下文，怎么防信息失真？【进阶】

**背诵版**：三个纪律：① **结构化交接**：交接载荷用结构化格式（状态/已完成/待办/关键事实），别靠自然语言段落自由发挥；② **产物落盘+引用**：大块产物（文档、代码）写文件传引用，摘要只传要点——「仓库产物+600 字摘要」模式；③ **职责单一化**：每个 agent 只对一块负责，链式审校要清楚**验的是交接一致性还是事实正确性**（下游验不出上游源头自洽的错误，这是链式审校的结构性盲区）。

**追问**：Q：子 agent 要不要带主对话全史？→ 不要，带任务说明+必要背景即可——fresh context 正是子 agent 的价值。

### Q6. LangGraph 的 StateGraph 核心概念？和「while 循环调模型」差在哪？【必背★】

**背诵版**：三件套：**State**（带 reducer 的共享状态——每个字段声明合并策略，如覆盖式 `(_a,b)=>b` 或累加式），**Node**（拿到 state 返回 state 增量的函数），**Edge/条件边**（含循环边——图可以回头，这是超越线性 chain 的关键）。和裸 while 循环的差异是**图即声明**：拓扑显式可测（条件边的分支逻辑是纯函数，可以零 token 单测）、中断/恢复/持久化是框架能力（自己写循环这些全要手造）、执行路径可追溯。**什么时候值得上图**：流程有分叉/循环/人工介入点；纯线性「调一下模型」用循环就够了，上图是过度工程。

**追问**：Q：reducer 写错会怎样？→ 状态合并语义错（该累加的被覆盖），图还照跑——静默状态错误。Q：节点返回全量还是增量？→ 返回增量，框架按 reducer 合并。

### Q7. checkpointer 为什么是生产必需？【必背★】

**背诵版**：checkpointer 给图执行加**持久化快照**：每个超级步（节点执行完）存一份状态。三个用途：① **断点恢复**——进程崩了/用户关页了，从最近快照续跑（thread_id 定位会话）；② **human-in-the-loop**——interrupt 挂起后状态完整落库，人回来再 resume；③ **时间旅行/审计**——历史快照可查可回放（从某步重分支）。实现选型：SqliteSaver（单机）、PostgresSaver（生产）。**工程要点：快照是序列化冻结**——存的是深拷贝不是引用，节点里原地改 state 对象会污染历史快照（要改就返回新对象让框架走 reducer）。

**追问**：Q：thread 是什么粒度？→ 会话级身份（如 `practice:{sessionId}`），同 thread 跨场延续历史。Q：快照存哪就安全了吗？→ 敏感对话内容进库要考虑加密与保留策略。

### Q8. interrupt 机制怎么工作？做 human-in-the-loop 有什么坑？【必背★】

**背诵版**：interrupt 是图内的**挂起点**：节点执行到 `interrupt(payload)` 暂停，状态落库，payload（如题面/审批卡）给到外部；人通过 `Command({resume: value})` 恢复，**恢复值作为 interrupt 的返回值**回到该节点继续。关键语义：① **resume 从挂起节点重放，不重跑已过节点**——所以「每场重置」这类逻辑放 start 节点，resume 路径不会再次经过它，fresh 和 resume 天然分径；② **挂起时输入校验前移**：用 responseSchema 把非法恢复值（如空字符串）当场炸掉，别让脏数据落库后再处理；③ 挂起期间状态在 checkpointer 里，服务重启也不丢。

**追问**：Q：挂起多久会失效？→ 取决于持久化寿命（sqlite 里就是永久的），业务上自己加过期策略。Q：人和自动化怎么混在一个图里？→ interrupt 之外还可以用「等待节点+外部事件」，interrupt 是最直给的人工闸。

### Q9. LangChain 生态里 createAgent / StateGraph / deepagents 怎么选？【进阶】

**背诵版**：三档抽象：**createAgent**（v1 预制单 agent：模型+工具+可选 checkpointer，几分钟搭起来，定制点少）；**StateGraph**（手写图：节点/边/reducer 全自控，适合强流程——出题循环、审批门、多阶段流水线）；**deepagents**（框架级深度 agent：内置规划/文件系统/子 agent 的一整套 harness，适合**开放探索型任务**——研究、长程自主工作）。选型判据是**流程确定性**：拓扑确定、失败零容忍的流程用 StateGraph 显式写；开放探索交给 deepagents 类 harness；简单问答 createAgent 足矣。**认知前提：三档都读得懂在做什么**——手写过原理层，框架就只是语法糖而不是黑盒。

**追问**：Q：deepagents 的文件系统是沙箱吗？→ 默认不是（virtualMode 默认关，绝对路径原样放行），沙箱语义要自己确认配置，别拿默认配置当安全边界。

### Q10. 框架、手写、低代码平台（Dify/coze 类）怎么选型？【必背★】

**背诵版**：**低代码平台**：非工程团队快速搭原型、标准场景（客服、知识库问答），上限是平台的组件边界，复杂逻辑和可靠性工程无处安放；**框架（LangGraph 等）**：工程团队的性价比选择——持久化/流式/中断这些脏活有人管，图逻辑自己写，可测试可部署；**手写**：学习原理（人人都该手写一遍）或极端定制（框架抽象成为阻碍时）。给面试的诚实答案：**先手写搞懂原理，再用框架提效，平台只用于非工程场景**——三者不是站队而是分层。判断一个团队该用哪个：看有没有工程资源维护自研、流程是否标准化。

**追问**：Q：手写一遍的价值到底在哪？→ 出问题能定位到协议/框架层（比如 custom 事件通道不生效是写入姿势问题不是业务 bug），不手写的人只能瞎猜。

### Q11. 子 agent 的上下文怎么设计？【进阶】

**背诵版**：子 agent 的价值一半在隔离，所以上下文设计就是「**给多少、收什么**」：给——任务说明+必要背景+自己的工具面（不给主对话全史，防污染防膨胀）；收——**结构化结果而不是自由文本**（schema 约束产出：结论/要点/数据），大块产物落盘传引用。权限面也要收：子 agent 尽量只读（取材/分析），要写就单独过确认门。终止上子 agent 更容易失控（没人看着），机械闸（maxCalls 强制收敛）是标配。

**追问**：Q：子 agent 失败了怎么办？→ 主 agent 收到失败语义自己决策（重试/换路/放弃），别让子 agent 异常炸穿主循环。

### Q12. agent 循环的可靠性，除了终止闸还有哪些闸？【进阶】

**背诵版**：一套最小可靠性件：① **机械终止闸**（Q1）；② **fail-closed 解析**——结构化输出解析失败一律回落安全路径（重试或降级），绝不带着半解析状态继续跑；③ **abort 归因**——先查 signal.aborted 再归错误，把「用户主动取消」和「真故障」分开，否则取消会污染可靠性统计和告警；④ **预算闸**——token/时间/调用数三重上限，超了走人话化的收尾而不是硬崩；⑤ **半截落盘语义**——流式输出中途断开，已生成部分按明确规则处理（保存并标注未完），别静默丢。共同原则：**每类失败都有明确的归宿，没有「静默」这个选项**。

**追问**：Q：这些闸怎么测？→ 注入 fake 模型/工具构造失败剧本，零 token 回归测试钉住每个闸的行为。
