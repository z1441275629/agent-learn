# 01 · LLM 基础与 API

> 覆盖：token 与上下文 / 采样参数 / 结构化输出 / 流式 / 多模态 / 幻觉 / 模型选型。目标：API 层的题答不出，后面 Agent 全白搭——这章是地基。

### Q1. 什么是 token？为什么所有计费、限流、上下文限制都按 token 算？【必背★】

**背诵版**：token 是模型处理文本的最小单位，由分词器（tokenizer）把文本切成子词——常见英文单词约 1 个 token，中文一个汉字通常 1~2 个 token，所以**中文的 token 成本系统性高于英文**。计费按 token 因为推理算力随 token 线性（注意力随长度平方级）增长；限流按 token 因为上下文窗口是稀缺资源。工程上要有 token 直觉：估算 prompt 成本、判断上下文会不会爆、决定哪里该裁剪。

**追问**：Q：怎么估算一段中文的 token 数？→ 粗算「字数 × 1.5」，要精确用 tokenizer 库或 API 的 usage 字段对账。Q：为什么截工具结果比截对话历史划算？→ 工具结果（网页、日志）往往占大头且信息密度低，性价比最高。

### Q2. 上下文窗口是什么？超出了会发生什么？【必背★】

**背诵版**：上下文窗口是单次请求能装下的 token 上限（prompt + 历史 + 生成全部算在内）。超出的行为分两种：API 直接报错（需自己截断），或服务端静默截掉最前面的内容——**静默截断比报错危险**，模型「忘了」system prompt 或早期约束还照样回答。工程对策：usage 对账监控余量、超限前主动压缩（摘要旧轮次/截断工具结果），不能依赖服务端兜底。

**追问**：Q：上下文越长模型越好用吗？→ 不一定，「lost in the middle」：长上下文中间部分召回率下降，关键信息要放开头结尾。Q：你的项目怎么管理上下文？→ 超预算时旧轮摘要+增量原文、滑动窗口兜底，摘要失败回落安全路径。

### Q3. temperature 和 top_p 分别控制什么？判定类任务该设多少？【必背★】

**背诵版**：都是采样随机性参数。temperature 对概率分布整体缩放：<1 收敛（高概率词更突出）、>1 发散；top_p（nucleus）只从前缀累积概率达 p 的候选集里采样，是「截尾」。**两者只调一个即可**，同时调会互相干扰。经验值：判官/抽取/分类/结构化输出 = 0（要稳定可复现）；创作/头脑风暴 = 0.7~1.0；日常对话 0.3~0.7。**判定节点锁 temperature=0** 是 agent 工程纪律，不锁的话同一输入两次评分不同，评测就失效了。

**追问**：Q：temperature=0 就完全确定了吗？→ 不保证，批推理/GPU 非确定性仍可能有微小浮动，别把可复现性全押在它上面。Q：max_tokens 是采样参数吗？→ 不是，它是长度预算，管的是生成上限不是随机性。

### Q4. 除了 temperature/top_p，还有哪些采样与输出控制参数？【进阶】

**背诵版**：frequency_penalty / presence_penalty 抑制重复（前者按出现次数、后者按是否出现过）；stop 序列硬停；seed 尽力对齐复现（多数厂商不保证严格一致）；logprobs 拿候选词概率做置信度分析；reasoning effort / 思考预算类参数控制推理型模型的思考深度——**深度档位是成本杠杆**，简单任务降档能省大量 token。

**追问**：Q：模型输出重复啰嗦先调什么？→ 先查 prompt 是否诱导重复，再试 frequency_penalty 小正值，别一上来换模型。

### Q5. 怎么让模型稳定输出结构化 JSON？说三种方案和取舍。【必背★】

**背诵版**：① **JSON mode / 结构化输出 API**：厂商在解码层强制合法 JSON（或 json_schema 约束），最可靠，但绑平台能力；② **函数/工具参数强制**：把目标结构定义成 tool 的 parameters schema，模型「调用工具」时参数即结构化输出，跨厂商兼容性最好，因为 function calling 是各家都支持的成熟通道；③ **prompt 约定 + 校验重试**：prompt 里给 schema 和 few-shot，输出后 zod/JSON Schema 校验，失败把错误信息回喂重试。**工程标配是 ②或①做第一层，③做兜底层**——解析失败一定要 fail-closed（回落安全路径），不能让坏 JSON 流进下游。

**追问**：Q：为什么工具参数通道比裸 prompt 稳？→ 模型训练时工具参数有专门的对齐，且 SDK 侧有 schema 校验闭环。Q：markdown 围栏包着的 JSON 怎么办？→ 先剥围栏再 parse，剥完仍失败走重试——这是高频坑（PITFALLS 有账：catch 吞掉解析错会静默丢数据）。

### Q6. 为什么 agent 应用几乎都要流式输出？SSE 的原理是什么？【必背★】

**背诵版**：两个原因：**体验**——生成一个长答案要几十秒，不流式用户对着空白等待；**工程**——首 token 时间（TTFT）是可感知延迟的核心指标，流式让「开始出字」提前到一两秒，还能把整体超时拆碎。SSE（Server-Sent Events）是 HTTP 上的单向服务端推送：响应头 `Content-Type: text/event-stream`，-body 按 `event:`/`data:` 帧格式持续写，浏览器 EventSource 或 fetch 逐帧读。选它因为 LLM 响应天然是「服务端→客户端」单向流，SSE 比 WebSocket 轻（纯 HTTP、自动重连语义、穿代理友好），双向需求才上 WebSocket。

**追问**：Q：断线了怎么办？→ SSE 原生只在 EventSource 下自动重连，fetch 手撕的话要自己带 Last-Event-ID 语义重连补发——我的做法是服务端存会话快照，重连时补发挂起状态（如当前题面）而不是重放全流。Q：自定义事件怎么发？→ `event: xxx` 帧类型 + data 载荷，别把所有东西塞默认 message 通道。

### Q7. SSE 和 WebSocket 怎么选型？【进阶】

**背诵版**：单向服务端推送选 SSE：纯 HTTP、网关/代理兼容性好、自带重连语义、实现简单。需要客户端主动高频上行（协同编辑、游戏、双向 RPC）选 WebSocket。LLM 对话场景是「一问一答+服务端流」，用 SSE + 普通 POST 提交即可覆盖。注意 SSE 的坑：HTTP/1.1 下同域连接数限制、代理缓冲要把 `X-Accel-Buffering: no` 打开、断线检测要心跳。

**追问**：Q：为啥不用轮询？→ 轮询延迟高且空转浪费，流式场景轮询是反模式。

### Q8. 幻觉为什么会产生？工程上有哪些缓解手段？【必背★】

**背诵版**：成因是机制性的：模型本质是「下一个 token 概率分布」，训练目标是流畅合理而非事实正确，知识有截止日期，且会被 prompt 诱导「编一个像的」。**幻觉不能根除只能约束**。工程手段分层：① **检索锚定（RAG）**——答案必须来自给定材料，材料里没有就明说；② **结构化约束**——能 schema 化的任务不让自由文本发挥；③ **低温度**——判定/抽取场景锁 0；④ **可溯源**——输出带引用（来源、条目 id），批改判官锚定参考答案而不是自由发挥；⑤ **流程隔离**——高风险动作（写操作）过确认门，不让幻觉直接落地成破坏。

**追问**：Q：RAG 就不幻觉了吗？→ 检索错/材料冲突/模型无视材料都会，所以还要忠实性校验（答案是否真有材料依据）。Q：怎么量化幻觉？→ 评测集里放「知识边界题」（库里没有答案的问题），看模型会不会老实说不知道。

### Q9. 多模态输入是怎么工作的？图片消耗多少 token？【进阶】

**背诵版**：视觉模型把图片切块编码成视觉 token 序列，和文本 token 拼进同一上下文。计费按视觉 token 算：通常与分辨率挂钩（切块数随像素增长），高清大图可能顶几千上万 token——**多模态成本控制第一刀是压图**（缩分辨率、裁剪区域）。工程上常用「感知/推理分工」模式：小视觉模型先出结构化描述（截图里有什么、控制台报错是什么），主文本模型拿描述做推理决策——便宜且让各模型干擅长的事。

**追问**：Q：ASR/语音呢？→ 音频转 token 计费同理，客户端采集（如 Web Audio）压缩后走 ASR 转文字再进主模型，比直接音频进模型便宜得多。

### Q10. 给你一个新任务，怎么选模型？说你的权衡框架。【必背★】

**背诵版**：按四个维度打分再组合：① **能力**——任务类型（推理/代码/长文/多模态）匹配度；② **成本**——输入输出单价 × 预估量，长 prompt 场景输入价权重大；③ **延迟**——交互场景看 TTFT 和出字速度，批处理可以放宽；④ **生态/合规**——OpenAI 兼容协议（国内主流接入方式）、数据合规、部署方式。**实践上不是选一个模型而是路由**：把任务分档（主力/轻量/备用/视觉），简单任务（路由、摘要、判分）走轻量档省成本，主力档做难任务，备用档做容灾——这比全用一个贵模型省钱且抗单点。

**追问**：Q：怎么验证选对了？→ 小规模评测集（真实任务 20 个左右）跑对比，看成功率/成本/延迟三列，别只看官方榜单。Q：国产模型接入要注意什么？→ 基本都提供 OpenAI 兼容端点，SDK 换 baseURL 即可，但工具调用/流式细节有差异，要过一遍兼容性探针。

### Q11. system prompt 和 user prompt 有什么区别？为什么工具定义一般放 system？【进阶】

**背诵版**：system prompt 是全局指令层：设定角色、纪律、输出规范，优先级高于 user 消息，模型对它服从性更强；user 是单轮任务输入。工具定义放 system 侧（或 API 专用的 tools 字段），因为工具是「这个 assistant 能做什么」的稳定能力声明，不随轮次变化；且和 system 一起构成模型行为的固定约束层。工程纪律：**行为规则全进 system，user 只放任务数据**，别把纪律写在 user 消息里——会随对话被稀释。

**追问**：Q：多轮对话里 system 会被冲淡吗？→ 长上下文中间遗忘同样适用于 system，超长对话要压缩历史而不是动 system。

### Q12. 什么是推理型（reasoning）模型？什么时候值得开？【进阶】

**背诵版**：推理型模型在给出答案前先做长链思考（可显式输出思考过程或隐藏思考 token），在数学、代码、多步规划类任务上成功率显著更高，代价是：思考 token 也计费、延迟成倍增加、有时「过度思考」把简单任务复杂化。**决策规则**：规划/排障/复杂判断开高档；路由/抽取/格式转换降档或用非推理模型；另外注意思考内容在 API 里的暴露方式各厂商不同，别把思考文本误当正式答案喂给下游。

**追问**：Q：agent 里怎么组合？→ 我的实践：编排层规划师开思考档保步骤质量，执行层轻档省成本，审校节点降思考档还能降噪。
