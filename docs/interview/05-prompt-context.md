# 05 · Prompt 与上下文工程

> 覆盖：system 设计 / few-shot / CoT / 压缩裁剪 / 记忆系统 / 指令遵循排查。上下文工程是「模型时代的性能工程」——同样的模型，上下文管理差一个档位，效果差一截。

### Q1. system prompt 的设计原则？【必背★】

**背诵版**：把 system 当**行为宪法**写，四层结构：① **身份与目标**（你是谁、服务什么场景）；② **能力边界**（可用工具、什么时候用哪个、什么情况明说不知道）；③ **纪律与禁区**（禁止行为、安全边界、失败语义）；④ **输出规范**（格式、语言、结构化要求）。原则：规则全进 system、**user 消息只放任务数据**（纪律写 user 里会被对话稀释）；指令要短要硬（每条可执行可验证），长篇大论反而降低遵循度；关键规则放开头结尾（防 lost-in-the-middle）。system 是版本管理的对象——改 system = 改代码，要过评测。

**追问**：Q：system 和 developer 消息什么区别？→ 部分厂商多一层 developer 角色，优先级介于 system 和 user 之间，用于运行时注入的硬规则。Q：工具定义和 system 什么关系？→ 工具描述是 system 约束的延伸，行为规则别在两处重复定义（会打架）。

### Q2. few-shot 怎么用才有效？【必背★】

**背诵版**：few-shot 是用**示例定义分布**：模型从例子里学格式、口径、边界判断——比描述性语言更硬。要点：① 例子要覆盖**边界情况**（不只是 happy path：空输入怎么办、该拒绝的例子、格式特例）；② 例子顺序和一致性有影响（相同模式排列）；③ **警惕例子污染**：模型会模仿例子里的具体值（日期、名字、风格），别让示例数据渗进输出；④ 例子数量 2~5 个通常饱和，堆例子不如改描述。工程上例子放 system 或首条消息，保持稳定。**大量固定模式输出（成百上千条同格式任务）超出了 few-shot 的舒适区，那是微调的活**。

**追问**：Q：例子越多越好吗？→ 边际递减且挤占上下文，两三个高质量边界例胜过十个重复例。Q：怎么验证例子有效？→ 留一个测试 case 不放进示例，看模型能否泛化到它。

### Q3. CoT（思维链）什么时候用？什么时候有害？【必背★】

**背诵版**：CoT 让模型「先推理再作答」，在多步推理/数学/规划类任务上提升明显。实现从轻到重：prompt 里加「逐步思考」（老办法）→ 给带推理过程的 few-shot → 直接用推理型模型（训练级 CoT，质量最高）。**什么时候有害**：① 简单任务（分类、抽取、格式转换）上 CoT 纯烧 token 还增加跑偏面；② 判定/审校任务开满思考档会**过度分析产生噪声判定**（简单核对被想复杂了反而判错）——这类节点用轻档低思考。实践口径：**按节点分档**——规划/排障开思考，执行/判定降思考，这个分档本身就是成本工程。

**追问**：Q：思考过程能拿来用吗？→ 各厂商暴露方式不同，有的给思考块有的不给；别把思考文本当正式答案喂下游。Q：CoT 能保证推理对吗？→ 不能，步骤流畅≠结论正确，关键结论要有校验（审校/规则）。

### Q4. 上下文压缩怎么做？超预算了先砍什么？【必背★】

**背诵版**：超预算的裁剪优先级：① **先砍工具结果**（网页/日志这类大块低密度内容，性价比最高——截断+标注）；② **再压旧对话**（旧轮交轻量模型摘要落盘，之后每轮只发「摘要+增量原文」）；③ **最后动 system**（基本不动）。必备兜底：**摘要失败回落滑动窗口**（保留最近 N 轮原文）——压缩链路自己也会失败，没有兜底的压缩是把可靠性押给运气。工程细节：压缩是异步后台做还是同步做（同步增加延迟）；压缩触发点要留余量（别顶到上限才压，写一半被服务端截断最惨）。

**追问**：Q：摘要会丢信息怎么办？→ 接受有损但可控：摘要 prompt 里声明「保留事实、决策、待办」，丢寒暄不丢要点；关键事实可以结构化抽取单独存。Q：为什么不全量塞给长上下文模型？→ 贵，且 lost-in-the-middle 让中间内容召回率下降——长窗口≠免压缩。

### Q5. prompt 要不要版本管理？怎么改 prompt 才安全？【进阶】

**背诵版**：要——**改 prompt = 改代码**，且比代码更隐蔽（没有类型系统兜底）。纪律：① prompt 集中管理（模板+变量分离，别散在代码里）；② 修改走评测：固定评测集跑前后对比，关键指标不回退才合入；③ 留变更记录（谁、为什么、效果对比），面试讲「prompt 回归」很加分。进阶：重要 prompt 上 A/B 或灰度。**反面案例：校验规则改了提示词没跟着改**——两个真理来源渐行渐远，静默出错。

**追问**：Q：prompt 测什么指标？→ 任务成功率+格式合规率+关键禁令遵循率，按 prompt 的职责定。

### Q6. 长期记忆系统怎么设计？【必背★】

**背诵版**：四环节闭环：① **抽取**：回答后后台让模型抽取「值得长期记住的用户事实/偏好」（异步，不挡主流程）；② **守门**：抽取结果必须过校验——类型对（数组）、长度合理、**拒绝清空式输出**（一条校验 bug 会把整个记忆库清掉）；③ **注入**：跨会话把相关记忆注入 system（按相关性/时间选，不是全量倒进去）；④ **纠错**：支持单条删除/修改——记忆是会错的，没有纠错通道的记忆系统会持续污染对话。再加去重与合并（相似记忆成堆是常态，去重键要稳定）。**记忆的写路径永远过守门，读路径永远可控注入**。

**追问**：Q：抽取会不会夹带私货？→ 会——模型「好心」夹带推断建议，守门规则里明确只要事实不要推断。Q：记忆和 RAG 什么关系？→ 记忆是「关于用户的结构化事实」，RAG 是「知识检索」，实现可共用存储，语义不同。

### Q7. 记忆去重和时间锚怎么防漂移？【进阶】

**背诵版**：两个坑：① **去重键不稳定**——用「内容相似度」做去重，排版一变相似度跨阈值，相似记忆成堆；对策是**稳定键（内容哈希/规范化后的键）+ 相似度辅助**，不能只信相似度分数。② **时间锚被刷新**——合并记忆时把旧条目时间戳刷成现在，「老条目当锚」的排序逻辑全毁；合并要保留原始首次时间（最新更新时间可以另存）。原则：**记忆库是 append-mostly 的账本，不是覆盖式缓存**——每条记忆的来历和时间要可追溯。

**追问**：Q：冲突的记忆（用户先说 A 后说 B）怎么办？→ 带时间戳的覆盖语义：新事实取代旧事实但保留历史（可回溯），注入时只用当前有效集。

### Q8. 模型不遵守指令，怎么排查？【进阶】

**背诵版**：按可能性顺序排查：① **指令位置**——关键规则在上下文中段（lost-in-the-middle），移到开头结尾；② **指令冲突**——system/user/工具描述三处打架，模型选了别处的；统一真理来源；③ **长度稀释**——上下文太长指令被淹没，压缩或拆任务；④ **指令含糊**——「适当」「尽量」这类词不可执行，改成可验证的硬规则；⑤ **对抗内容**——工具结果/文档里的文本在对抗你的指令（间接注入），加来源标记隔离。**别一上来就换模型或加温度玄学调参**，先做这五步定位。

**追问**：Q：怎么区分「模型能力不够」和「prompt 问题」？→ 同 prompt 换更强模型试试：都错→大概率 prompt；强模型对弱模型错→能力边界。

### Q9. 给 agent 写 prompt 和给 chatbot 写，本质差异是什么？【必背★】

**背诵版**：chatbot prompt 优化「答得好」，agent prompt 要同时定义**机器可执行的行为契约**：① 工具使用规范（什么时候调、参数怎么填、结果怎么消化）——这是行为定义不是风格指导；② **终止语义**（什么情况给最终答案、什么情况明说做不到——别让它在循环里打转）；③ **失败语义**（工具报错怎么办、信息不足怎么办——降级路径写明）；④ 输出要考虑**下游消费者**（下一个节点/解析器是机器，格式稳定性优先于文采）。本质：agent prompt 的一半是**状态机定义**，写得像协议文档，而不只是像文案。

**追问**：Q：agent prompt 的回归怎么做？→ 行为契约的每条规则都要有对应测试任务（触发/不触发两向都测）。

### Q10. 长对话里 system 会被「冲淡」吗？怎么办？【进阶】

**背诵版**：会——注意力分配上，超长上下文中段（包括较早的指令）召回率下降，模型行为漂移。对策：① **压缩历史而不是动 system**（见 Q4）；② 关键规则在**最近上下文里重申**（每轮任务附带的硬提醒，比如工具调用的即时约束）；③ 把「必须遵守」的约束下沉到代码层（schema 校验、确认门）——**能用机制保证的别靠提示词维持**，这是最根本的防漂移。判断漂移：定期在长会话里探测关键规则遵循情况（探针任务）。

**追问**：Q：重申会不会自相矛盾？→ 重申要原文引用统一来源（模板变量），别手抄第二份（两份渐变=冲突源）。

### Q11. few-shot 和微调的边界在哪？【进阶】

**背诵版**：few-shot 解决「**这个任务的分布**」：例子随叫随到、改了立刻生效、零训练成本，但每轮都占上下文、上限受模型能力压制。微调解决「**稳定的行为模式**」：格式/风格/领域口径固化进权重，不占上下文、推理更快更便宜（小模型微调后干专项），代价是数据准备+训练+评估+维护、迭代慢、知识更新要重训。**判断信号**：示例多到挤占上下文（几十条起步）、且任务模式稳定不常变——该微调了。反过来：任务常变、要快速迭代、需要溯源——留在 prompt/RAG 层。

**追问**：Q：微调小模型 vs 直接用大模型 prompt？→ 算总账：调用量大到「大模型 token 费 − 小模型微调+推理费」为正才划算，低频场景永远大模型。
