# 09 · 项目深挖与场景设计

### Q1. 介绍一下你的 Agent 工作台。（电梯陈述，90 秒版）【必背★】

**背诵版**：「个人 Agent 工作台——12,000+ 行 TypeScript，全链路不依赖框架，从零手写。能力面：对话、13 个工具、Playwright 浏览器 Agent、语音输入、BM25 知识库、长期记忆、技能系统、定时任务、多 Agent 编排。核心是手写 ReAct 内核：流式 loop、同轮多工具调度（只读并发/写串行过确认门）、可靠性三件套（机械终止闸/fail-closed/abort 归因）。上面跑了多 Agent 流水线（研究→审校→写作→审校）和 Planner-Executor 编排，做了 Token 成本工程（全链路 usage 记账+源头截断）。质量有双层保证：16 个回归/E2E 套件 320+ 断言，加一个 20 任务端到端评估集（真实模型实测任务成功率 20/20、工具调用 26/26、invalid 0）。**它不是我写完就扔的 demo——我每天真实在用**，配了 MCP Server 把能力供给 Claude Code。」

**追问**：Q：为什么不用框架？→ 见 Q2。Q：数据量？成本？→ 日用对话+定时任务；成本靠分档路由和记账控制（讲机制不编幅度）。

### Q2. 为什么不用 LangChain 这些框架，全部手写？【必背★】

**背诵版**：三个理由：① **学习目的**——我要的是「懂原理」不是「快出 demo」：Function Calling 消息流时序、工具调度、终止控制这些，用框架永远隔着一层；手写一遍后框架对我只是语法糖——后来做 LangGraph 毕业项目、定位到框架层的静默缺陷（工具执行异步契约、custom 事件通道写入姿势），靠的正是原理层的底子；② **掌控可靠性边界**——终止闸、fail-closed、确认门这些保命机制，自己写的每一行都能说清楚为什么；③ **量级判断**——个人工具的复杂度还没到框架收益区，引框架反而多一层抽象债。**但我不反框架**：jobprep 毕业项目就是正经 LangGraph 工程——手写给了我选框架的自由，而不是被框架选。

**追问**：Q：手写最大的收获？→ 出问题能分层定位：先怀疑自己的代码，再怀疑用法，最后怀疑框架——每层都有实证手段，不瞎猜。Q：什么场景你会劝人直接用框架？→ 团队工程、要持久化/流式/中断这些基建、进度紧——框架是买时间。

### Q3. 同轮多工具调用，你为什么这么设计调度？【必背★】

**背诵版**：模型一轮返回多条 tool_calls 时：**只读工具并发执行（墙钟取 max），写工具严格串行过确认门**，但结果一律按 tool_calls **原序回填**——原序是 API 契约，乱序轻则报错重则模型误判因果；并发完成序和回填序解耦，是这个设计的核心点。写串行的理由：后面的决定应能看到前面写操作的结果，「本会话总是允许」这类授权也要顺序生效；确认卡一张一张出，不批量预批。验证：E2E 剧本钉死三性质——并发墙钟、串行卡序（ask→ok→ask→ok）、原序喂回。

**追问**：Q：并发会不会乱序写坏状态？→ 写操作天然串行不存在并发写；读并发无副作用。Q：如果厂商支持乱序回填呢？→ 契约按最严的写（原序），兼容面最大。

### Q4. 机械终止闸是什么？为什么需要？【必背★】

**背诵版**：子 agent/主循环调工具不收尾（一直「再查一下」不产出结论）时，**代码层按 maxCalls 硬闸：去掉 tools 再调一次，强制模型只用文字收敛**——不靠提示词里写「请及时停止」（对失控模型没有约束力）。配套的 fail-closed 解析：结构化输出解析失败一律回落安全路径（重试或降级），绝不带着半解析状态继续；abort 归因：先查 signal.aborted 再归错误，用户主动取消不污染可靠性统计。三件套的共同哲学：**每类失控都有确定性的机械处置，提示词是请求，代码才是约束**。

**追问**：Q：maxCalls 设多少？→ 按任务域标定（我的配置收紧过一轮——从宽到紧配合源头截断，具体参数讲配置不讲幅度）。Q：闸触发要不要告警？→ 记入失败分类统计（触发率异常升高=提示词或工具质量退化的信号）。

### Q5. ReAct 烧钱你真踩过吗？怎么治的？【必背★】

**背诵版**：踩过：一次任务 6 次工具调用能烧 6 万 prompt token——根因是 **ReAct 每轮重发全部历史**（system+全部对话+全部工具结果），成本按轮次平方级累加，大工具结果（整页网页）被反复重发。治理双管齐下：**源头截断**（工具结果限长+标注，砍掉重发的大头）+ **收紧机械闸**（轮次/调用上限调低，砍掉放大器）；再叠加全链路 usage 记账（路由/规划/审校每个环节的消耗都归因，编排层自身的隐形开销现形）。效果讲机制和参数变化，没有系统性 before/after 基准就不编百分比——这是我的证据纪律。

**追问**：Q：为什么不直接换长上下文便宜模型？→ 换模型是单价杠杆，截断是结构杠杆——结构问题先结构解决。Q：记账怎么落？→ 每次调用 usage 字段落盘，按节点/会话/天聚合。

### Q6. jobprep 的判官怎么防幻觉？（评分节点的设计）【必背★】

**背诵版**：三层锚定：① **温度 0**——判定节点锁参，保证同输入评分可复现（温度不锁，评测体系自己先不可信）；② **锚定参考答案**——judge 的 prompt 限定为「参考答案里的要点，用户答到什么程度」，只做要点比对不做知识发挥（judge 自由答题=幻觉重灾区）；③ **可溯源**——题库每题带 source 元数据，判官输出引用出处，题面/参考答案/批改三者可回查。输出结构化：分数+命中要点+遗漏要点+一句话点评——评分可审计而不只是一个数字。这道题的通用结论：**凡「判定」职责的节点，锚定+锁参+结构化输出是三件标配**。

**追问**：Q：judge 和人工不一致怎么办？→ 人工抽检校准（第 7 章 Q3 的方法论）。Q：judge 本身怎么测？→ 注入 fake 判官零 token 测图拓扑，真判官用金标样本校准。

### Q7. jobprep 入口为什么不做 LLM triage（语义路由）？【必背★】

**背诵版**：三个功能入口（陪练/培训/简历）用**显式页签直选，不上 LLM 语义分流**。理由：入口是**路由失败零容忍**的地方——用户点「陪练」进来去了「简历」，一次就失去信任；UI 确定性选择 100% 准，LLM 判定再高也有误判率。**LLM 判定的正确位置是真正需要模糊分流的场景**（比如意图理解、内容理解）。这是「确定性优先」选型原则的具体落地：先问这一步允不允许错，允许错才考虑模型，不允许就用确定性机制。同理的反例：判官要点比对必须懂语义——那是模型该干活的位置。

**追问**：Q：那什么场景你会上 triage？→ 用户输入开放、目标集合模糊、错误成本低（如闲聊 vs 任务的预分流，分错也能兜）。

### Q8. jobprep 抽题为什么不用向量检索？【必背★】

**背诵版**：题库百级规模、全量在内存，真实需求是**均匀轮换+错题优先+排除刚问过的**——是调度问题不是检索问题，直接纯函数实现（可单测、零成本、行为确定）。上向量检索是把「检索是瓶颈」的假设套在「均匀性才是瓶颈」的场景上——**技术选型先审需求，检索是伪需求时上检索是负资产**（多一套嵌入模型、多一层不可解释）。什么时候该上：题库万级、要按主题/相似度抽题、要相似去重——届时嵌入进 V2 候选。这题的 meta 答案：**每个「不用 X」的决策都要能说出「什么时候该用 X」——否则不是选型是偏见**。

**追问**：Q：错题优先怎么实现？→ 状态里记 askedIds/wrongIds，错题池优先（排除刚问的），池空回退未做均匀随机，再空全库随机——纯函数直测。

### Q9. 讲一个你踩得最深的坑。【必背★】

**背诵版**：讲「静默失败」系列（比异常难一个量级的是静默垃圾）：手动执行框架包装的工具拿到的是 Runnable，`String()` 强转把 **Promise 对象转成 "[object Promise]" 字符串**，不报错、喂给模型一坨垃圾——模型重试三次后道歉说「工具坏了」，它没说错，坏的是执行层；修法 await+并发 Promise.all，执行层加类型断言（非 string 一律炸）。另一个同类：LangGraph custom 流通道**三种写入姿势只有一种生效**，`dispatchCustomEvent` 根本不进通道、某个 `writer()` 导出静默空转——零事件零报错。两条的共同教训：**事件和结果要有对账（消费端实证），静默无事件比静默失败更隐蔽**——这类坑我攒了 76 条，每条带复现条件和修复方案。

**追问**：Q：怎么系统性发现这类问题？→ 零 token 探针先行：不接模型先验证执行层/事件通道（消费端数事件条数），再往上叠。

### Q10. 讲讲你在公司做的 AI 助手（龙虾），以及你怎么看它的局限。【必背★】

**背诵版**（⚠️ 事实需本人核对）：「蓝湖期间（2026 年上半年）我搭了公司 AI 研发助手：基于 Agent 平台配置了开发/答疑两个子助手——开发侧依托 MasterGo 插件 API 类型包和开发规范辅助插件开发，答疑侧接插件文档知识库服务外部插件开发者；接入了飞书/企微/微信三端机器人，做了权限边界的控制。数据：日均 10+ 条答疑、自助解决率 75%。**坦白说它很初级**：平台黑盒，我做的本质是提示词层调优和知识库组织，出问题只能改 prompt 碰运气，说不清底层为什么。**这正是我离职后从 Function Calling 消息流开始系统重学的原因**——我想要的是能对每一层负责的工程能力，现在的仓库就是这个决心的证据。」

**追问**：Q：那段时间最大的收获？→ 见识了 AI 助手在真实组织的落地形态（用户是谁、回答边界、知识库维护），知道了一个黑盒系统「能用」和「可控」之间的差距。Q：如果重做龙虾你会怎么做？→ 自研内核+框架基建、评估集先行、判答可溯源——把现在个人工作台这套方法论搬过去。

### Q11. 场景设计题：从零设计一个「智能客服 agent」，说你的方案。【进阶】

**背诵版**（答题框架，现场展开）：① **意图分层**：高频确定性问题（订单查询/退改规则）走 RAG+模板，确定性操作走工具（带确认门），复杂投诉转人工——**先分类再动用 agent，全对话 agent 是烧钱**；② **知识底座**：产品文档/FAQ 离线索引（chunking+混合检索+rerank），答案带引用来源；③ **工具面**：查询类直连业务 API（只读免确认），操作类（退款/改地址）过确认门+幂等；④ **安全**：间接注入防御（用户消息和知识库内容标不可信）、PII 脱敏进日志；⑤ **人工升级**：升级判据（情绪/多轮未解决/高价值客户）+ 完整上下文交接给人工；⑥ **评测与监控**：离线评测集（含知识边界题/该升级题）+ 线上解决率/转人工率/成本监控，坏例回流。**亮点句：设计的每个分支都在回答「错了怎么办」**。

**追问**：Q：怎么控制成本？→ 意图分流（简单问题不进 agent）+模型分档+缓存高频问答。Q：怎么防答错承诺（说错退款政策）？→ 关键政策答案锚定知识库原文+引用展示，政策类问题禁止自由发挥。

### Q12. 场景设计题：把你的个人工作台改造成团队版，要加什么？【进阶】

**背诵版**（⚠️ 口径需本人核对）：先讲**做过的反面决策**：我给日报系统做过多租户 v2（用户/邀请码/会话隔离），复盘结论是**单人场景的多租户是伪需求**——复杂度翻倍、没有第二个真实用户验证，已终止。所以团队版第一步不是写代码，是回答三个问题：**几个用户、什么共享、谁付费**。真要加，按优先级：① **账号与会话隔离**（认证+每会话独立 checkpointer 命名空间）；② **权限与审计**（工具权限按角色收敛、写操作审计日志——个人版的确认门升级为审批流）；③ **成本分账**（usage 记账从个人统计升级为按用户/团队配额——记账底座已有，加维度而已）；④ **部署形态**（状态外置、密钥管理、多实例）。**核心卖点：个人版把可靠性/记账/安全的底座打好了，团队化是加维度不是重构**。

**追问**：Q：最容易被低估的难点？→ 记忆和知识库的共享语义——个人记忆混进团队上下文是事故（PII+错位），要按用户/团队两级隔离设计。
