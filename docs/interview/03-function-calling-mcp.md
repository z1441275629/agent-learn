# 03 · Function Calling 与 MCP

> 覆盖：消息流时序 / schema 设计 / 并行调度 / 错误与重试 / MCP 协议 / 工具安全。工具是 agent 的手——这一章答不好，「Agent 开发」四个字立不住。

### Q1. 说一遍 function calling 的完整消息流时序。【必背★】

**背诵版**：① user 发问 → ② 模型返回 assistant 消息，带 `tool_calls`（工具名+JSON 参数），**此时模型不产答案只产调用意图**；③ 客户端本地执行工具（模型碰不到你的机器）；④ 把结果包成 `tool` 角色消息（带 tool_call_id）追加进消息列表；⑤ 再调模型，它基于结果继续——要么再发起调用（循环），要么给出最终文本。**关键认知：工具执行权永远在客户端，模型只是「请求」执行**；多条 tool_calls 要按原序逐条回填结果，这是 API 契约。所谓 agent loop 就是把这个循环包起来跑到出现纯文本为止。

**追问**：Q：为什么模型不能直接执行工具？→ 安全与确定性的分界线，执行侧可以做确认门/守门/审计。Q：工具结果太大怎么办？→ 截断+标注（「已截断至 N 字」），别静默腰斩。

### Q2. 工具的 schema 怎么设计？描述到底写给谁看？【必背★】

**背诵版**：**描述是写给模型看的 prompt**，不是给开发者的注释——模型选工具、填参数全靠它。设计要点：① 命名用动词+宾语自解释（`search_kb` 好过 `kb`）；② description 说清「什么时候该用、什么时候不该用、返回什么」，边界写明（「查询个人笔记，不要用于时事」）；③ 参数最少化，每个参数带描述和约束（枚举/最小值），能用 required 锁死就锁死；④ 返回值结构稳定、错误人话化（模型要能读懂错误自己纠正）。**反面教材：枚举示例被模型当白名单、参数描述含糊导致 invalid-call**——schema 质量直接决定调用成功率。

**追问**：Q：工具越少越好吗？→ 不是越少越好而是「描述可辨析」——两个工具描述区分度不够，模型就会乱选。Q：怎么发现 schema 有问题？→ 看 invalid-call 和选错工具的 case，改描述再回归。

### Q3. 模型一轮里返回多个工具调用，怎么调度执行？【必背★】

**背诵版**：先分类再调度：**只读工具并发执行**（无副作用，墙钟取 max 省时间）、**写工具严格串行**（后面的决定能看到前面的结果，副作用可控）。但无论执行序怎么乱，**结果必须按 `tool_calls` 的原序回填**给模型——这是 API 契约，乱序部分厂商直接报错。并发完成序与回填序解耦，是同轮多调用的核心工程点。写操作前面还要过确认门（参数亮卡、批准才执行），一张一张出，不批量预批。

**追问**：Q：为什么写操作不能并发？→ 并行副作用时序不可控，且「本会话总是允许」这类授权要顺序生效。Q：只读一定安全吗？→ 还要过 URL 守门（拒 file:// 等），「读」也能读出注入。

### Q4. 工具执行出错了，是抛异常还是把错误喂回模型？【进阶】

**背诵版**：**能喂回的都喂回**：把错误包装成工具结果（isError 语义）返回模型，让它自己决定重试、换参数还是放弃——模型有纠错能力，前提是错误信息人话化（「URL 拒绝：协议不在白名单」而不是堆栈）。**该炸的才炸**：结构性错误（工具不存在、参数 schema 不过）说明调用层坏了，喂回也没意义，记日志走降级。别让异常直接打断 agent loop——工具失败≠循环失败，区分「这一步失败」和「整个任务失败」。

**追问**：Q：模型反复重试同一个失败工具怎么办？→ 机械闸兜底（maxCalls），超限强制收敛；错误信息里给替代建议。

### Q5. 重试和幂等怎么设计？【必背★】

**背诵版**：分两层。**传输层重试**：网络错误/限流用指数退避自动重试，这里天然幂等（请求没到达）。**工具层重试**：模型改参数重试或重复调用——写操作没有幂等保护就会重复下单/重复写入。设计原则：① 写工具尽量幂等（幂等键、upsert 语义）；② 做不到幂等的写操作过确认门，每次执行都让用户看见；③ 给模型的错误信息里说清「已执行了一半」这类部分成功状态，别让它盲目重跑。**agent 场景的重试主体是模型不是你的代码**——你提供干净的错误语义，它提供决策。

**追问**：Q：timeout 算成功还是失败？→ 不确定态最危险，超时要当「未知」处理（查询确认），不能默认失败重试。

### Q6. 工具一多模型就选错，怎么治理？【进阶】

**背诵版**：工具数量上去后全量塞 schema 会稀释注意力、选错率上升。治理路线：① **描述辨析化**（治本，见 Q2）；② **分组/分级加载**：常用工具常驻，长尾工具收进检索——给模型一个 `search_tools` 元工具按需查可用工具（渐进式披露，对齐 Claude 的 Skills 思路）；③ **路由分层**：先按意图分流到子 agent，每个子 agent 只带自己域的工具（工具面小=选择准）。注意索引摘要本身别膨胀，否则披露机制自废武功。

**追问**：Q：多少个工具算多？→ 没有硬线，看描述区分度；invalid-call 率上升就是信号。

### Q7. MCP 是什么？解决什么问题？【必背★】

**背诵版**：MCP（Model Context Protocol）是**模型与外部能力之间的开放协议**——把「工具/资源/提示词的供给方」和「消费方（Claude Code、IDE、自研 agent）」解耦：供给方实现一次 MCP Server，所有支持 MCP 的客户端都能用；消费方接一次协议，就能用全世界的 Server。类比 USB-C：以前每个工具每个客户端单独接线（N×M），现在统一接口（N+M）。核心概念：Server 暴露 tools/resources/prompts 三类能力，客户端通过 initialize 握手、tools/list 发现、tools/call 调用。价值判断：**个人闭环用不上，跨客户端/跨工具复用才值得**。

**追问**：Q：MCP 和 function calling 什么关系？→ function calling 是模型能力（会发起调用），MCP 是工具供给协议（工具从哪来）；MCP tools 最终还是转成 function calling 喂给模型。

### Q8. 手写一个 stdio MCP Server，关键实现点有哪些？【必背★】

**背诵版**：① **传输**：stdin/stdout 按行读 JSON-RPC（单行一条），日志走 stderr 别污染协议通道；② **initialize 握手**：客户端先发 initialize（带协议版本与能力声明），服务端回显协商版本，握手完成前不处理业务请求；③ **错误两层**：协议错（未知方法/参数缺失）走 JSON-RPC error（-32601/-32602，连接不断）；执行错走结果的 isError 字段喂回模型（模型能看到并自我纠正）——**混用会让可恢复错误变成断连**；④ **优雅退出**：close 前排干在途异步应答（在途计数归零再收资源），否则异步工具的应答被截断；⑤ stdout 单行序列化，别打印调试信息到 stdout。

**追问**：Q：为什么日志必须走 stderr？→ stdout 是协议通道，混入非 JSON 行直接破坏协议。Q：版本协商不一致怎么办？→ 回退双方都支持的最高共同版本，或明确报错，别静默装兼容。

### Q9. 什么时候值得引入 MCP，什么时候直接定义 function calling 就够？【进阶】

**背诵版**：判断标准是**复用面**：工具只在自研 agent 里用，直接代码定义最简单，MCP 是多余一层；能力要供给多个客户端（Claude Code、IDE 插件、同事的 agent 共用），或要消费第三方 MCP Server 快速扩能力，MCP 的解耦才回本。附带收益：外部供给的工具自带审批语义（客户端逐个批准写操作）。附带成本：进程管理、协议版本、调试链路变长。**别为了简历好看加协议层**——先问有没有第二个消费方。

**追问**：Q：MCP Server 的写操作安全吗？→ 协议本身不管安全，审批语义在客户端实现；自研时要配 kill-switch（只读模式开关）。

### Q10. 工具安全怎么设计？说你的分层。【必背★】

**背诵版**：四层防线：① **分组分权**：只读/写入分组，写操作过**确认门**（参数原文亮卡、批准才执行、超时拒绝）；② **输入守门**：URL 协议白名单（http/https，拒 file://javascript:/data:）、路径防逃逸；③ **内容隔离**：外部内容（网页/文档）标记不可信哨兵，防 tool poisoning 和间接注入——外部文本里的「指令」不是指令；④ **总闸**：kill-switch 一键只读。原则：**权限默认最小，升级需人工**；模型是善意但不稳定的执行者，安全边界不能依赖提示词自觉。

**追问**：Q：为什么确认门要亮参数原文？→ 模型转述可能美化/省略，用户要看到真实执行的值。Q：只读工具就不设防吗？→ 读外网内容就有注入面，来源标记不能少。

### Q11. 怎么评估一套工具集设计得好不好？【进阶】

**背诵版**：看三个指标：① **invalid-call 率**（调用参数过不了 schema——描述不清的直接信号）；② **选对工具率**（该用 A 时用了 B——描述辨析度问题）；③ **任务完成率**（工具粒度对不对、返回信息够不够模型决策）。方法：固定任务评测集跑真实模型，把每次调用的期望工具/顺序/禁止项写进判分（不只是最终答案对不对，过程也要对）；坏例回改 schema 描述再回归。**工具集是迭代出来的，不是设计出来的**。

**追问**：Q：过程判分怎么落？→ 每任务标注期望工具序列与禁止工具，执行后比对 trace。

### Q12. 框架里工具对象和普通函数有什么区别？【进阶】

**背诵版**：以 LangChain 为例：`tool()` 包装后拿到的是 **Runnable**，不是原函数——`invoke()` 是异步契约，**同步函数包装后也返回 Promise**。手写执行层时图省事 `String(result)` 会静默拿到 `[object Promise]` 喂给模型（模型还会礼貌道歉说工具坏了，其实是执行层错了）。正确姿势 `await` + 需要并发就 `Promise.all`。这条的普适教训：**框架的类型契约要敬畏，静默类型强转比异常危险一个量级**——异常会炸给你看，垃圾字符串会一路流进模型上下文。

**追问**：Q：怎么提前发现这类问题？→ 执行层加结果类型断言（非 string 一律炸），零 token 探针先验证执行层再接模型。
