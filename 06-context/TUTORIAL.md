# 模块 06 · 上下文工程——我用三周手写的东西

> 写法提醒：这是给未来自己和面试官看的教程。**用自己的话写**，代码在旁边，重点是「为什么这么设计」。每节末尾的问题先自问自答再下笔。写完脱稿讲一遍，讲不顺的段落就是没懂的地方。

## 0. 问题：上下文为什么需要「工程」

- RAM 类比：窗口是什么、为什么稀缺（用你自己跑出来的数字说话：一次 search_notes 就吃掉 72%）
- 提示工程 vs 上下文工程的区别（只管怎么问 vs 管整个窗口里放什么）

## 1. 先测量，再优化

- 四桶打表：system / 历史 / 工具定义 / 工具结果——**工具定义不在 messages 里但照样计费**（多少人的盲区）
- 估算器怎么校准：字符启发式 → `usage.prompt_tokens` 对表，误差 11% → 5%
- 校准系数是**模型相关的**；估算器的用途是决策阈值，不是计费
- 我的数字：____（把开/关管理的对比表贴进来）

## 2. 武器①：工具结果截断（源头减量）

- 为什么性价比最高：在结果进 messages **之前**砍
- 工具级配置 `maxResultTokens`：每个工具的返回量级要想清楚（配置本身是设计动作）
- 字符级截断的局限 + 金笔记实验的结论：____（agent 无视「家里已有 3 把伞」了吗？）
- 排序是截断做不到的事 → 为什么真实 RAG 靠 top-k 少而精

## 3. 武器②：compaction（有损压缩）

- 什么时候值得：压缩花一次 LLM 调用，之后每轮省 X——**break-even 几轮**（我的数字：____）
- 摘要 prompt 的四要素：任务目标 / 决定及依据 / 关键数字 / 未完成
- 轮（turn）的定义；为什么摘要边界必须落在轮与轮之间
- 一次 compaction 发生时 messages 数组从什么变成什么（脱稿讲 2 分钟的那段，写下来）

## 4. 武器③：滑动窗口（存量兜底）

- 为什么它治不了我的 72%——「保新弃旧」撞上「污染是新的」
- 优化层级：**源头减量 → 存量控制 → 有损压缩**，便宜的先做，贵的少触发（我的实测：截断上线后窗口再没触发过）

## 5. 架构：双账本 ContextManager

- ledger（底账，只增不删）+ view（发送视图）；为什么这个设计让「重赋值断引用」的 bug 结构性消失
- 前缀稳定性与 prompt caching（不变内容排前，可变排后——为什么省钱）
