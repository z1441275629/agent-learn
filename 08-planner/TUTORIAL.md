## 0. 问题：ReAct 的天花板

- 衔接 07：记忆解决「记得住」，调度解决「做得长」——任务一复杂，走一步看一步就开始兜圈
- ReAct（走一步看一步）vs plan-then-execute（先出地图再行军）各适合什么任务——我的对比数据在 §6
- 预埋三个核心问题：重试怎么保证幂等？子任务失败几次该扔掉整张计划？计划赶不上变化时谁说了算？

## 1. Planner：把复杂任务变成结构化计划

- zod schema 定义计划：步骤列表（id / 描述 / 依赖 / 状态 pending|running|done|failed）
- 计划生成：一次 LLM 调用产出 JSON——parseModelJson + zod 双保险（07 的教训：模型输出格式永远不可信）
- 计划常驻上下文：每次请求把**最新计划状态**注入 system——计划是 working memory 里的钉子，模型每一步都看得见地图（对比 07 的索引常驻：同一个模式的复用）
- 打勾更新：执行完一项改状态、重新注入——「你每天看的 todo 进度条」背后就是这套

## 2. Executor：逐项执行 + 重试 + replan

- 执行循环：取下一个依赖已满足的 pending 项 → 执行 → 打勾 → 下一个
- 失败重试：次数上限；重试前先问——**这个工具重跑一遍安全吗（幂等）？**
  - 幂等的（读类 / search）随便重试；非幂等的（write_memory、发消息、下单）重试 = 重复副作用——07 的审计日志就是现成证据
- replan 触发条件（想清楚再写码）：连续 N 次失败 / 执行中发现计划前提错了 / 全部 done 但任务没完成——把当前进度 + 失败原因喂回 planner 重新出图
- replan 也要有熔断：重规划本身连续失败 N 次就停，别无限套娃

## 3. 并发：无依赖的子任务并行

- 依赖图：互不依赖的 pending 项打进**同一个请求的多个 tool_calls**（07 循环里的 Promise.all + tool_call_id 配对早就在做，现在把它提到计划层用）
- 加速比测量：串行 vs 并发跑同一任务，记墙钟时间 + token——模块 06 的纪律：成本数字配结果看
- 并发坑预告：写类工具并发互相踩（07 里「Promise.all 并发写同名文件互相覆盖」的注释就是预告）；完成顺序 ≠ 提交顺序
