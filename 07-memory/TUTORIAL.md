## 0. 问题：会话结束了，ledger 也死了

- 和模块 06 的衔接：窗口/截断/压缩全是会话内的，记忆 = 上下文的二级存储（RAM → 硬盘）
- 四层记忆框架：working / episodic / semantic / procedural（各举一个我自己记忆库里的真实例子）

## 1. 文件型记忆（第一通道）

- 布局：MEMORY.md 索引（一行一条）+ memories/*.md（一事实一文件）；为什么索引常驻、正文按需读
- **渐进式披露的决策规则**：披露防的是「单条大」，检索防的是「数量多」——search 已经筛过「多」，top-k 是最相关的内容，单条不大就给全文（我的 search_memory 返回全文的理由）
- 写入策略 A：模型自主决定记什么——description 怎么写（判断标准先行，例子只做示意）
- 治理三件：去重（内容相同跳过）、覆盖（审计日志 + `flag:'a'`）、更新路径（「我改主意了」）

## 2. 检索型记忆（第二通道）

- 手写向量库：embed + cosine + top-k + vectors.json 持久化（约 50 行，pgvector/Milvus 本质就是这三件事 + 近似索引）
- 双通道分工：索引精确点名 vs 语义模糊检索；read_memory vs search_memory 不打架
- 探针数据（贴我的实测）：语义查询 / 实体查询的分数差异——「媳妇叫什么」0.408 vs 0.407 的掷硬币
- 结论：纯向量在实体查询上排序是浆糊 → BM25 混合检索的立项理由
